% Abstract
% ============================================================
\begin{abstract}
Post-compromise recovery in an asynchronous messaging protocol is a timed process, not a
binary switch.  Fresh randomness, authenticated KEM delivery, and cached out-of-order keys
jointly determine how long an exposure persists and when a session crosses back into a fresh
state.  We make this interval explicit as a \emph{recovery window} and study its interaction
with the classical-DH exposure window in Star-Mesh, an asynchronous hybrid ratchet combining
X25519 with ML-KEM-768.

We introduce (i) a state machine for one-time, authenticated ML-KEM ratchet exchanges with replay,
loss, duplication, and out-of-order handling; (ii) a game-based recovery definition with
explicit assumptions for delivery, RNG recovery, and secret deletion; and (iii) a conditional
security bound for message keys derived after a completed fresh KEM round-trip.  The resulting
analysis provides a concrete recovery bound: after compromise, if the endpoint's identity signing key
survives uncompromised (e.g., hardware-backed in a secure enclave), the post-recovery ML-KEM keypair
is generated with clean randomness, the authenticated exchange completes, and the tested message key is not
an already exposed skipped key, the bound is
\[
\begin{aligned}
  \Adv_{\mathrm{PCS}}(\mathcal{A})
  \;\leq\;&
  Q_{\mathrm{sess}}Q_{\mathrm{upd}}Q_{\mathrm{KEM}}\,
  \Adv_{\mathrm{ML\text{-}KEM}}^{\mathrm{ind\text{-}cca2}}(\mathcal{B}_{\mathrm{KEM}})\\
  &+ 2Q_{\mathrm{sess}}Q_{\mathrm{upd}}\,
  \Adv_{\mathrm{ML\text{-}DSA}}^{\mathrm{euf\text{-}cma}}(\mathcal{B}_{\mathrm{DSA}})\\
  &+ Q_{\mathrm{KDF}}\,\Adv_{\mathrm{KDF}}^{\mathrm{hi}}(\mathcal{C})
  + \negl(\lambda).
\end{aligned}
\]
Here $Q_{\mathrm{sess}},Q_{\mathrm{upd}},Q_{\mathrm{KEM}},Q_{\mathrm{KDF}}$ are explicit
polynomial query bounds defined in Section~\ref{sec:prelim}; $\Adv^{\mathrm{hi}}_{\mathrm{KDF}}$
is the dual-PRF / extractor KDF advantage defined there.  Crucially, PCS holds only
if the identity signing key remains uncompromised across state compromise; if an adversary exfiltrates
the identity key alongside live ratchet state, post-compromise recovery is unachievable because the
adversary can forge update signatures.  The ratchet heals continuous message confidentiality after
transient state leaks, relying on the hardware-isolated identity key strictly to authenticate the
healing KEM transition against active substitution.  Before a fresh KEM update completes, a
quantum adversary who compromises live state recovers intermediate messages across the pre-recovery
exposure window ($\Delta$ messages of counter delay plus network round-trip latency, potentially
unbounded if the peer is offline).  The ratchet interval $\Delta$ therefore becomes a tunable systems
parameter: it amortises KEM traffic while setting the baseline pre-recovery exposure.  The theorem is
about this recovery transition, rather than continuous post-quantum confidentiality or a
complete UC realization.

We instantiate the state machine with ML-KEM-768 and ML-DSA-65 and report its cryptographic wire cost
($88.90$ amortised bytes/message for alternating initiations at $\Delta=50$, up to $177.80$~B/msg in
worst-case concurrent dual-initiation, with 4-packet Sphinx fragmentation per update).  A Rust
prototype exercises the concurrent buffer, authenticated headers, erasure, and bidirectional
convergence, while ProVerif checks selected symbolic invariants.  Together these artifacts make
the recovery transition concrete; the DHT and mixnet are the deployment setting in which the
transition operates, not additional security claims of this paper.
\end{abstract}

\section{Introduction}
% ============================================================

The imminent threat of Cryptographically Relevant Quantum Computers (CRQCs) has accelerated the
standardization of post-quantum cryptographic (PQC) algorithms by NIST, notably ML-KEM
\cite{nist_fips203} and ML-DSA \cite{nist_fips204}.  While traditional secure messaging
protocols such as Signal have begun integrating PQC \cite{signal_pqxdh} to defend against
``Harvest Now, Decrypt Later'' (HNDL) attacks \cite{mosca2018cybersecurity}, they rely
predominantly on centralized servers for key distribution and message routing.

This centralization creates a single point of failure for both availability and metadata
privacy: a server compromise can reveal the social graph, timing information, and message volume
of all users, even when message contents are encrypted.  Decentralized alternatives such as
Session \cite{session_protocol} and Briar \cite{briar_design} mitigate this architectural risk
through onion-routing networks, but they remain committed exclusively to classical
elliptic-curve primitives (X25519), leaving them vulnerable to HNDL attacks.

\paragraph{Our Approach.}
We formulate post-compromise recovery as a \emph{windowed state transition}.  Instead of
assuming that a successful KEM exchange instantaneously heals a session, the model tracks the
interval from clean randomness and authenticated update creation through delivery, ordered
application, erasure, and the first testable post-update key.  This exposes the precise point
at which recovery becomes meaningful and separates it from the messages that remain vulnerable
before that point.  Star-Mesh instantiates this transition with an asymmetric KEM rather than a
commutative DH exchange, combining NIST PQC standards
\cite{nist_fips203,nist_fips204} with the classical Double Ratchet structure, while treating
the Kademlia DHT and mixnet as deployment context rather than as contributions proved by this
paper.

\paragraph{Security boundary.}
The central theorem concerns one fixed pairwise session and one or more authenticated,
deterministically ordered ML-KEM recovery updates.  Its freshness predicate requires a target
KEM keypair sampled after RNG recovery, an unrevealed recovery identity key, and erasure of the
target KEM secret, old root/chain keys, and excluded skipped keys before the target message key
is tested.  The security model explicitly separates ephemeral session state from the long-term
identity signing key: the state compromise query returns volatile runtime state (ephemeral
chain/root keys, entropy pool, pending ciphertexts, and cached message keys) but does not reveal
the ML-DSA signing key.  PCS holds strictly under the condition that the identity signing key
remains uncompromised (e.g., protected by a hardware security module or secure enclave); if total
device expropriation compromises the signing key, recovery is impossible.  The ratchet's PCS adds
critical protection beyond static identity keys: static identity keys provide authentication rather
than confidentiality, whereas the ratchet continuously refreshes the quantum-resistant symmetric
confidentiality root, using the hardware-isolated identity key strictly to prevent active MITM
key substitution during healing.  Delivery remains fully adversarial: delay, duplication, reordering, modification,
and loss are modeled, with an update becoming a confidentiality target only after it completes.
This boundary isolates the cryptographic recovery transition from DHT availability, mixnet
anonymity, UC composition, side channels, and quantum claims about X25519.

\paragraph{Hybrid Security Rationale.}
Star-Mesh is a \emph{hybrid} protocol: X25519 remains a classical component, while ML-KEM-768
provides the recovery contribution against a quantum-capable adversary.  Accordingly, the
paper's quantum-facing claim is deliberately about the post-recovery transition, not every
property of the surrounding deployment: X25519 remains classical and ML-DSA carries the
quantum-resistant identity binding.  A fresh ML-KEM exchange and its authenticated delivery
are the mechanism by which the session crosses from the exposure window into the recovered
state.

Formally, the hybrid shared secret is computed as
\[
  SS_{\text{hybrid}} = \hexlit{0xFF} \;\|\; SS_{cl} \;\|\; SS_{PQ1} \;\|\; SS_{PQ2}
\]
passed through HKDF-SHA3-256 with the ciphertexts $ct_1, ct_2$ and the classical ephemeral public key $EK_{pk,A}$ bound into the KDF input string $info$. The concatenation-combiner analysis of Giacon et al.\ \cite{giacon2018kem} motivates this construction, but it is not a direct proof of the complete Star-Mesh protocol: the classical DH component, authenticated asynchronous delivery, deletion schedule, and hidden-input KDF composition require the protocol-specific games and assumptions stated below. Binding the transcript (ephemeral key and ciphertexts) is intended to satisfy the combiner's ciphertext-binding precondition and to limit related-ciphertext/re-encapsulation attacks. HKDF is modeled as a PRF in the proof sketches (see Assumption~\ref{asm:hkdf} in Section~\ref{sec:secmodel}), while the complete post-recovery composition uses Assumption~\ref{asm:kdf-hi}.

\paragraph{Trust Assumptions on Infrastructure.}
Star-Mesh is \emph{decentralized in deployment}, not trust-free.  The DHT nodes collectively
control availability of key bundles; a Sybil attack can eclipse a user's mailbox.  The mixnet
requires that fewer than a fraction $f$ of mix nodes are compromised (the Loopix assumption
\cite{loopix}).  These operational assumptions are stated explicitly in
Section~\ref{sec:assumptions}.

\paragraph{Contributions.}
\begin{enumerate}
  \item \textbf{State machine:} An asynchronous ML-KEM ratchet with authenticated identifiers,
        one-time secret deletion, replay rejection, and explicit handling of loss, duplication,
        delay, and out-of-order delivery.
  \item \textbf{Recovery game:} A freshness definition and PCS game that make RNG recovery,
        delivery completion, deletion, and pre-existing skipped-key exposure explicit.
  \item \textbf{Exposure analysis:} A conditional proof target for message keys derived after a
        completed fresh KEM round-trip, together with an informal characterization of the
        pre-recovery exposure window ($\Delta$ messages plus round-trip latency, unbounded if the
        peer is offline) prior to recovery completion.
  \item \textbf{Executable correspondence:} A Rust prototype that exercises the concurrent
        buffer, authenticated headers, erasure, and bidirectional convergence, together with
        ProVerif models checking selected symbolic state-machine properties.
\end{enumerate}

\paragraph{Scope and Proof Status.}
The main result is a concrete, pairwise recovery theorem with explicit freshness and delivery
semantics.  The additional game-based arguments in Section~\ref{sec:security} extend the same
construction and are labeled proof sketches where their reductions are not fully mechanized or
tight in a composable framework.  A complete UC-style treatment of the protocol is left to future work \cite{uc_framework}.  To complement the proof-sketch arguments, we provide a machine-checked
ProVerif~\cite{proverif} model
(\texttt{formal/pq\_x3dh.pv} and \texttt{formal/ratchet.pv} in the repository) that verifies,
in the symbolic Dolev-Yao model, the following properties: session-key secrecy under long-term
key reveal, MITM resistance via bundle-signature authentication, pre-compromise forward secrecy,
PCS healing after one complete PQ round-trip, and the skipped-key cache caveat
(Corollary~\ref{cor:pcs}, Caveat~2).  These are supplementary symbolic checks and do
not replace the computational reductions; they provide independent evidence of the protocol
logic against a symbolic adversary.

\paragraph{UC formulation status.}
The repository now specifies a candidate ideal functionality $\mathcal{F}_{\mathrm{SM}}$ in
\texttt{docs/uc-formulation.md}.  It exposes registration, asynchronous delivery, ratchet epochs,
state compromise, recovery, and an explicit mixnet leakage interface rather than assuming perfect
traffic-flow hiding.  This is a proof target and not a theorem: a UC realization claim requires a
real/ideal interface, an environment and simulator, composable corruption semantics, and a
computational indistinguishability proof.  In particular, the existing pairwise games and
ProVerif models do not establish UC security.

\paragraph{Research Positioning.}
Star-Mesh should be viewed as a protocol-design and analysis contribution rather than a
production-ready messaging system.  The present manuscript focuses on architectural synthesis,
adversarial modeling, and hybrid post-quantum ratcheting semantics in a preprint setting,
where the goal is to surface a precise design and a clear security model for peer review.
A production deployment would additionally require extensive implementation hardening,
empirical evaluation, interoperability testing, and operational abuse-resistance analysis.

\subsection{Notation}

We write $\lambda$ for the security parameter.  A function $f(\lambda)$ is \emph{negligible}
(written $f \in \negl(\lambda)$) if for every polynomial $p$, $f(\lambda) < 1/p(\lambda)$ for
all sufficiently large $\lambda$.  We write $x \getsr S$ for sampling $x$ uniformly at random
from a finite set $S$, and $x \getsr \mathcal{D}$ for sampling from a distribution
$\mathcal{D}$.  We denote by $\|$ the concatenation of byte strings.

All query bounds below are functions of $\lambda$ and are polynomially bounded.  For an
adversary $\mathcal A$, let $Q_{\mathrm{sess}}$ bound the number of candidate target-session
selections, $Q_{\mathrm{upd}}$ bound authenticated recovery-update attempts per session,
$Q_{\mathrm{KEM}}$ bound the number of KEM challenge embeddings or challenge-relevant
encapsulations considered by a reduction, and $Q_{\mathrm{KDF}}$ bound the number of
post-recovery KDF outputs replaced in a hybrid.  These are upper bounds supplied to the
reduction; they are not protocol constants and are not additional security assumptions.  The
symbol $\negl(\lambda)$ absorbs correctness and encoding-collision terms under the stated
implementation model.  ML-KEM shared secrets and message keys have 256 bits in the concrete
instantiation, but the asymptotic security parameter remains $\lambda$.

We write $\flen{s}$ for the \emph{fixed-width, 4-byte big-endian} encoding of the byte length
of string $s$.  Using a fixed-width encoding prevents length-extension ambiguity when multiple
variable-length fields are concatenated.

For key derivation, $\HKDF(ikm, salt, info, \ell)$ denotes HKDF-SHA3-256 with input key
material $ikm$, optional $salt$, context $info$, and output length $\ell$ bytes.  SHA3-256 is
the underlying hash function; it is \emph{not} modeled as a random oracle in this work; rather
HKDF is modeled as a two-stage extract-then-expand PRF following the HKDF construction in
RFC~5869 \cite{rfc5869} and its formal analysis by Krawczyk (CRYPTO 2010)
\cite{krawczyk2010hkdf} (see Assumption~\ref{asm:hkdf} in
Section~\ref{sec:secmodel}).

\begin{definition}[Dual-PRF / Extractor KDF Advantage]
\label{def:kdf-hi}
Let $F(ikm, salt, info, \ell)$ be an extract-then-expand KDF (e.g., HKDF-SHA3-256).
The \textbf{one-uniform-component extractor game} models settings where the
input key material $ikm$ is formed by concatenating $m \geq 1$ components,
\[
  ikm = c_1 \,\|\, c_2 \,\|\, \dots \,\|\, c_m,
\]
such that at least one designated component $c_j = u \in \bits^{k}$ is computationally
uniform and hidden from the adversary, while the remaining components $p = (c_i)_{i \neq j}$
(which may include fixed domain-separation constants, adversarially known classical DH secrets,
or pre-key shared secrets) are known to or chosen by the adversary.  The game proceeds as follows:
\begin{enumerate}
  \item The challenger receives the adversary's choice of public/adversarial components $p$ and
        context $(salt,\, info)$.  The salt may be public/fixed (e.g.\ $salt = \mathbf{0}^{32}$
        in the initial handshake) or secret/fresh (e.g.\ the entropy pool $EP'$ or root key $RK$
        in ratchet updates).
  \item The challenger draws an independent uniform hidden component $u \getsr \bits^{k}$,
        constructs $ikm$ with $c_j = u$ and $c_{i \neq j} = p_i$, computes
        $y_0 = F(ikm,\; salt,\; info,\; \ell)$, and draws an independent uniform string
        $y_1 \getsr \bits^{\ell}$.  It samples $b \getsr \{0,1\}$ and returns
        $(y_b,\, p,\, salt,\, info)$ to the distinguisher $\mathcal{C}$.
  \item $\mathcal{C}$ outputs a guess $b' \in \{0,1\}$.
\end{enumerate}
The advantage is $\Adv^{\mathrm{hi}}_{F}(\mathcal C) \coloneqq |\Pr[b'=b]-\tfrac{1}{2}|$.

\noindent\textbf{Justification of one-uniform-component sufficiency.}  HKDF computes
$\mathsf{PRK} = \mathsf{HMAC}_{salt}(ikm)$ during extraction and expands it via
$\mathsf{HKDF\text{-}Expand}(\mathsf{PRK}, info, \ell)$.
Following Krawczyk's dual-PRF analysis \cite{krawczyk2010hkdf}:
\begin{itemize}
  \item \textbf{Public/zero salt (handshake):} When $salt = \mathbf{0}^{32}$ is a fixed public
        constant, HMAC acts as a PRF keyed by its input data (the dual-PRF property).  Because
        $u$ is computationally uniform and statistically independent of $p$, $u$ provides the
        secret keying material that ensures the extracted $\mathsf{PRK}$ is computationally
        indistinguishable from uniform, despite the known prefix or suffix $p$.
  \item \textbf{Secret/fresh salt (ratchet):} When $salt$ is secret and high-entropy (e.g.\ $EP'$
        derived from preceding ratchet epochs), HMAC acts as a standard PRF keyed by $salt$,
        and extraction holds \emph{a fortiori} with dual-source entropy from both $salt$ and $u$.
  \item \textbf{Expansion:} The expand step evaluates HMAC in standard PRF mode keyed by the
        pseudorandom $\mathsf{PRK}$, guaranteeing that output key material $y_0$ is computationally
        indistinguishable from a uniform bitstring of length $\ell$.
\end{itemize}
In security reductions, replacing the target shared secret (e.g.\ $SS_{PQ2}$ in the handshake, or
$SS_{PQ}$ in the ratchet) with a uniform string $u$ via KEM IND-CCA2 satisfies the input requirement.
The $\Adv^{\mathrm{hi}}_{F}$ term isolates KDF extraction/expansion security from KEM IND-CCA2
hardness, preventing circularity and double-counting.
\end{definition}

\subsection{Key Encapsulation Mechanisms}

\begin{definition}[KEM]
A Key Encapsulation Mechanism $\Pi = (\KeyGen, \Encaps, \Decaps)$ consists of three algorithms:
\begin{itemize}
  \item $\KeyGen(1^\lambda) \to (pk, sk)$: Generates a public/secret key pair.
  \item $\Encaps(pk) \to (ct, ss)$: Encapsulates, producing ciphertext $ct$ and shared secret $ss$.
  \item $\Decaps(sk, ct) \to ss$: Decapsulates, recovering $ss$ (or $\bot$ on failure).
\end{itemize}
\end{definition}

\begin{definition}[IND-CCA2 KEM Security]
Let $\Pi = (\KeyGen, \Encaps, \Decaps)$ be a KEM.  The advantage of adversary $\calA$ in the
IND-CCA2 game is:
\[
  \Adv^{\mathrm{ind\text{-}cca2}}_{\Pi}(\calA) \coloneqq \left| \Pr\left[
  \begin{array}{l}
    (pk, sk) \getsr \KeyGen(1^\lambda); \\
    (ct^*, ss_0) \getsr \Encaps(pk); \\
    ss_1 \getsr \bits^{|ss_0|}; \\
    b \getsr \bits; \\
    b' \getsr \calA^{\Decaps(sk,\cdot)}(pk, ct^*, ss_b) : \\
    \quad b' = b
  \end{array}
  \right] - \frac{1}{2} \right|
\]
where $\calA$ may not query $\Decaps(sk, ct^*)$.  We say $\Pi$ is IND-CCA2 secure if
$\Adv^{\mathrm{ind\text{-}cca2}}_{\Pi}(\calA) \in \negl(\lambda)$ for all PPT $\calA$.
\end{definition}

\subsection{Digital Signature Schemes}

\begin{definition}[EUF-CMA Security]
A signature scheme $\Sigma = (\KeyGen, \Sign, \Verify)$ is Existentially Unforgeable under
Chosen-Message Attacks (EUF-CMA) if for all PPT adversaries $\calA$:
\[
  \Adv^{\mathrm{euf\text{-}cma}}_{\Sigma}(\calA) \coloneqq \Pr\left[
  \begin{array}{l}
    (vk, sk) \getsr \KeyGen(1^\lambda); \\
    (m^*, \sigma^*) \getsr \calA^{\Sign(sk,\cdot)}(vk) : \\
    \quad \Verify(vk, m^*, \sigma^*) = 1 \\
    \quad \wedge\ m^* \notin \mathcal{Q}
  \end{array}
  \right] \in \negl(\lambda)
\]
where $\mathcal{Q}$ is the set of queries made to the signing oracle.
\end{definition}

\subsection{Cryptographic Primitives in Star-Mesh}

Star-Mesh instantiates the following standardized primitives:

\begin{itemize}
  \item \textbf{Identity Signatures:} ML-DSA-65 (Dilithium3) \cite{nist_fips204}, a
        lattice-based signature scheme whose security reduces to the hardness of Module-LWE and
        Module-SIS.
  \item \textbf{Key Encapsulation:} ML-KEM-768 (Kyber768) \cite{nist_fips203}, an IND-CCA2
        KEM whose security reduces to Module-LWE with parameters $n = 256$, $k = 3$.  Public
        key size: 1184 bytes; ciphertext size: 1088 bytes; shared secret: 32 bytes.
  \item \textbf{Classical DH:} X25519 \cite{rfc7748}, a Diffie--Hellman function over
        Curve25519.  Key and output size: 32 bytes each.  X25519 is vulnerable to a CRQC; it
        is retained for hybrid security against classical adversaries only.
  \item \textbf{Key Derivation:} HKDF-SHA3-256 \cite{rfc5869} for all key derivation steps
        (see Assumption~\ref{asm:hkdf}); BLAKE3 \cite{blake3} for message key derivation within
        the symmetric ratchet.
  \item \textbf{AEAD Encryption:} AES-256-GCM \cite{nist_aesgcm} with 96-bit nonces and
        128-bit tags.
\end{itemize}

\subsection{Parameter Selection and Security Categories}
\label{sec:paramselection}

To establish concrete security levels and estimate protocol overhead, Star-Mesh instantiates FIPS 203 and FIPS 204 parameters aligned with NIST Security Category~3 (providing key-search security equivalent to AES-192). Specifically, we select ML-KEM-768 for post-quantum key encapsulation and ML-DSA-65 for identity signatures. This selection represents a deliberate balance of security, communication bandwidth, and computational cost under decentralized mixnet constraints:

\begin{itemize}
  \item \textbf{Comparison with Category 1 (ML-KEM-512 and ML-DSA-44):} While Category~1 primitives provide smaller public key sizes (e.g., 800~B for ML-KEM-512) and marginally faster execution times, they only offer AES-128 equivalent security. We opt for Category~3 to align with standard high-security targets (AES-192/256) and to provide a wider margin of safety against future algebraic/structural advances in lattice attacks.
  \item \textbf{Comparison with Category 5 (ML-KEM-1024 and ML-DSA-87):} Category~5 provides the highest standardized security (AES-256 equivalent) but introduces substantial bandwidth penalties. ML-DSA-87 signatures exceed $4.5$~KB, and ML-KEM-1024 public keys ($1{,}568$~B) exceed a standard 1{,}500-byte MTU by themselves. In a decentralized mixnet architecture like Loopix/Sphinx, messages are routed in constant-sized packets (MTUs) to prevent traffic analysis. Under Category~5, periodic signed updates would require fragment trains of 6 or more packets, severely degrading queue throughput.
\end{itemize}

Thus, Category~3 (ML-KEM-768 and ML-DSA-65) is selected as the default parameter set for Star-Mesh.  The resulting packetization discipline distinguishes routine conversational messages from periodic authenticated ratchet updates:
\begin{enumerate}
  \item \textbf{Intermediate Conversational Messages Fit Under MTU:} Routine messages ($\Delta - 1$ out of every $\Delta$ messages) carry only 32-byte classical X25519 ratchet headers and application payloads ($192$~B payload $+$ $32$~B header $+$ $96$~B Sphinx framing $= 320$~B).  These fit comfortably within a standard $1{,}500$-byte Ethernet/Sphinx MTU without fragmentation.
  \item \textbf{Periodic Signed Ratchet Updates Fragment into 4-Packet Trains:} Because state compromise is silent and undetectable, achieving post-compromise security (Theorem~\ref{thm:single-update-pcs}) mandates that \emph{every} periodic KEM update carries mutual ML-DSA-65 signatures ($\sigma_{\mathrm{init}}$ and $\sigma_{\mathrm{resp}}$, $3{,}309$~bytes each).  The initiator payload ($1{,}184$~B ML-KEM pk $+$ $3{,}309$~B signature $+$ $192$~B application payload $= 4{,}685$~B) and responder reply ($1{,}088$~B ML-KEM ct $+$ $3{,}309$~B signature $+$ $192$~B application payload $= 4{,}589$~B) exceed $1{,}500$~B and are fragmented by the transport layer into trains of 4 Sphinx packets per update direction.
  \item \textbf{Handshake and Pre-Key Bundle Fragmentation:} Initial handshake messages ($M_0 = 4{,}256$~B, consisting of $4{,}224$~B raw cryptographic payload plus $32$~B framing/identifiers) and signed DHT pre-key bundles (including 3{,}309-byte ML-DSA-65 signatures) also exceed $1{,}500$~B.  With a per-packet Sphinx payload capacity of $1{,}404$~B ($1{,}500$-byte MTU minus $96$-byte Sphinx header), transmitting $M_0$ requires a 4-packet Sphinx train ($\lceil 4{,}256 / 1{,}404 \rceil = 4$, and even the raw cryptographic core requires $\lceil 4{,}224 / 1{,}404 \rceil = 4$) or asynchronous DHT mailbox deposits.
\end{enumerate}

\section{The Star-Mesh Protocol}
\label{sec:protocol}
% ============================================================

\subsection{Overview and Trust Model}
\label{sec:trust}

Star-Mesh is a decentralized protocol deployed without central servers; all key-distribution
operations are performed over a Kademlia DHT \cite{kademlia}.  Users are identified by their
ML-DSA-65 public key $IK^{DSA}$.  Out-of-band verification (e.g., key fingerprint comparison,
QR codes) is assumed for initial identity binding, following standard practice in secure
messaging \cite{marlinspike_x3dh}.

\textbf{DHT trust assumption.}  The DHT stores and serves Pre-Key Bundles but is \emph{not}
trusted for their authenticity: all bundles are signed under the owner's $IK^{DSA}_{sk}$ and
verified by recipients.  However, DHT nodes collectively control availability; a Sybil attack
can eclipse a user's mailbox.  We assume the DHT is Sybil-resistant as an operational
assumption (see Section~\ref{sec:assumptions}).

\textbf{Mixnet trust assumption.}  Message delivery is routed through a mixnet overlay.  We
assume at most a fraction $f < 1/2$ of mix nodes are adversarially controlled, following the
Loopix threat model \cite{loopix}.

\subsection{Key Generation and Identity}

Each node derives its cryptographic material from a 256-bit master seed
$\mathsf{seed} \getsr \bits^{256}$ via deterministic key generation.  A 256-bit seed aligns
the root-of-trust entropy with the Category~3 security margin targeted by the ML-KEM-768 and
ML-DSA-65 parameter choices (Section~\ref{sec:paramselection}).  A node's \emph{Identity
Bundle} comprises:
\begin{itemize}
  \item $IK^{DSA} = (IK^{DSA}_{pk}, IK^{DSA}_{sk}) \getsr \MLDSA.\KeyGen(1^\lambda)$: the
        long-term identity signing keypair.
  \item $IK^{DH} = (IK^{DH}_{pk}, IK^{DH}_{sk}) \getsr X25519.\KeyGen$: the long-term
        classical DH keypair.
  \item $SPK = (SPK_{pk}, SPK_{sk}) \getsr X25519.\KeyGen$: a semi-static signed pre-key,
        rotated periodically (e.g., weekly).
  \item $PQ\_SPK = (PQ\_SPK_{pk}, PQ\_SPK_{sk}) \getsr \MLKEM.\KeyGen(1^\lambda)$: a
        semi-static ML-KEM pre-key, rotated after a bounded number of uses.
  \item $\{OTPK_i\}_{i=1}^{n}$: a batch of $n$ one-time X25519 pre-keys.
  \item $\{PQ\_OTPK_j\}_{j=1}^{m}$: a batch of $m$ one-time ML-KEM pre-keys.  Consumption of
        at least one $PQ\_OTPK$ is \emph{mandatory} when available to guarantee initial PQ
        forward secrecy (see Section~\ref{sec:fsremark}).  When the batch is exhausted, only
        $PQ\_SPK$ is used; in that case, the session achieves \emph{session-level} PQ-FS (the
        pre-key is ephemeral per session) rather than \emph{one-time pre-key PQ-FS} (the
        pre-key is used exactly once, then zeroized).  See Remark~\ref{rem:spkonly} for the
        precise distinction.
\end{itemize}

\subsection{Pre-Key Bundle Publication}
\label{sec:bundle}

Node $A$ publishes the following signed bundle to the DHT, keyed by $H(IK^{DSA}_{pk,A})$:
\[
  \mathsf{Bundle}_A = \bigl(IK^{DSA}_{pk}, IK^{DH}_{pk}, SPK_{pk}, PQ\_SPK_{pk},
                             \{OTPK_{pk,i}\}_{i}, \{PQ\_OTPK_{pk,j}\}_{j}, \sigma\bigr)
\]
The signature $\sigma$ is computed over \emph{all} public pre-key material to prevent
substitution of individual pre-keys by a DHT adversary:
\begin{align*}
      \mathsf{BundlePayload} &=
                        \strlit{StarMesh-Bundle-v1} \;\|\;
                        IK^{DSA}_{pk} \;\|\; IK^{DH}_{pk} \;\|\;
                        SPK_{pk} \;\|\; PQ\_SPK_{pk} \\
        &\quad\|\; \flen{\bigcat{i}{OTPK_{pk,i}}}
             \;\|\; H\!\left(\bigcat{i}{OTPK_{pk,i}}\right) \\
        &\quad\|\; \flen{\bigcat{j}{PQ\_OTPK_{pk,j}}}
             \;\|\; H\!\left(\bigcat{j}{PQ\_OTPK_{pk,j}}\right) \\[4pt]
  \sigma &= \MLDSA.\Sign(IK^{DSA}_{sk},\; \mathsf{BundlePayload})
\end{align*}
where $H$ is SHA3-256 and $\bigcat{i}{X_i} = X_1 \| X_2 \| \cdots$ denotes the ordered
concatenation of all keys in the batch (not XOR; we use $\|$ throughout for concatenation).
Signing the hashes of the full OTPK and PQ-OTPK batches (rather than individual keys) binds
the entire batch to $\sigma$ without inflating the signed payload size; an adversary cannot
substitute any identity key, pre-key, or individual OTPK/PQ-OTPK without invalidating
$\sigma$.  A fetcher must also reject a record unless its DHT lookup key equals
$H(IK^{DSA}_{pk})$ from the signed bundle; the signing key is therefore not chosen solely
from an attacker-controlled record.

Any node fetching $\mathsf{Bundle}_A$ verifies $\sigma$ against the reconstructed
$\mathsf{BundlePayload}$ and checks the lookup-key equality before use.

\begin{remark}
\label{rem:spkonly}
\textbf{Session-level vs.\ one-time pre-key PQ-FS.}  When a PQ-OTPK is consumed, its secret
is zeroized immediately after a single decapsulation; subsequent sessions receive a distinct
one-time pre-key.  This gives \emph{one-time pre-key PQ-FS} for the handshake: even revealing
the long-term $IK^{DH}_{sk}$ and $PQ\_SPK_{sk}$ after the fact does not expose the session's
shared secret, because $PQ\_OTPK_{sk}$ is gone.

When the OTPK batch is exhausted, the initiator encapsulates only against $PQ\_SPK$.  Because
$PQ\_SPK$ is reused across multiple sessions before rotation, an adversary that obtains
$PQ\_SPK_{sk}$ can retroactively recover the shared secret of all sessions that used it.  We
term this \emph{session-level} PQ-FS: forward secrecy holds at the granularity of $PQ\_SPK$
rotation epochs, not per session.  Implementations should replenish OTPK batches proactively to
minimize exposure in this mode.
\end{remark}

\subsection{Hybrid PQ-X3DH Handshake}
\label{sec:x3dh}

Alice (initiator) fetches Bob's bundle from the DHT, verifies $\sigma_B$
over $\mathsf{BundlePayload}_B$, and executes the handshake. The design extends Signal's
X3DH \cite{marlinspike_x3dh} with parallel ML-KEM encapsulations.

\paragraph{Step 1 --- Classical X3DH Component.}
Alice generates a fresh ephemeral keypair $EK_A \getsr X25519.\KeyGen$ and computes:
\begin{align*}
  DH_1 &= \DHop(IK^{DH}_{sk,A},\; SPK_{pk,B}) \\
  DH_2 &= \DHop(EK_{sk,A},\; IK^{DH}_{pk,B}) \\
  DH_3 &= \DHop(EK_{sk,A},\; SPK_{pk,B}) \\
  DH_4 &= \DHop(EK_{sk,A},\; OTPK_{pk,B}) \quad \text{(if available; omitted otherwise)}
\end{align*}
The classical shared secret is $SS_{cl} = DH_1 \| DH_2 \| DH_3 \| DH_4$.

\paragraph{Step 2 --- Post-Quantum KEM Component.}
Alice encapsulates against Bob's ML-KEM pre-keys:
\begin{align*}
  (ct_1,\; SS_{PQ1}) &\getsr \MLKEM.\Encaps(PQ\_SPK_{pk,B}) \\
  (ct_2,\; SS_{PQ2}) &\getsr \MLKEM.\Encaps(PQ\_OTPK_{pk,B}) \quad \text{(if available)}
\end{align*}

\paragraph{Step 3 --- Cryptographic Binding and Key Derivation.}
The Associated Data binds the handshake to both parties' post-quantum signing identities,
preventing identity misbinding and Unknown Key-Share (UKS)-class attacks (originally
demonstrated for STS) \cite{blake1997unknown}:
\[
  AD = \strlit{StarMesh} \| \flen{IK^{DSA}_{pk,A}} \| IK^{DSA}_{pk,A}
                           \| \flen{IK^{DSA}_{pk,B}} \| IK^{DSA}_{pk,B}
\]
To satisfy the IND-CCA2 security precondition of the concatenation/split-key combiner proved by Giacon et al.~\cite{giacon2018kem}, the KEM ciphertexts and the classical ephemeral public key are bound into the HKDF input. The binder string $info$ is constructed by appending the length-prefixed transcript parameters to $AD$:
\[
  info = AD \| \flen{EK_{pk,A}} \| EK_{pk,A} \| \flen{ct_1} \| ct_1 \| \flen{ct_2} \| ct_2
\]
The hybrid input key material is formed by combining classical and post-quantum secrets with a
domain-separation prefix byte $\hexlit{0xFF}$ (following the Signal Protocol convention
\cite{signal_pqxdh}; see also \cite{bindel2018hybrid} for hybrid KEM domain separation):
\[
  SS_{\text{hybrid}} = \hexlit{0xFF} \| SS_{cl} \| SS_{PQ1} \| SS_{PQ2}
\]
The 64-byte Output Keying Material is then:
\[
  OKM = \HKDF\!\left(ikm = SS_{\text{hybrid}},\; salt = \mathbf{0}^{32},\;
                     info = info,\; \ell = 64\right)
\]
\textbf{Rationale for $salt = \mathbf{0}^{32}$ at initialization.}  RFC~5869
\cite{rfc5869} states that when no truly independent salt is available (as is the case at the
start of a fresh handshake where no prior shared state exists), a zero salt is acceptable: the
HKDF extract step still provides entropy concentration from the IKM.  In contrast, subsequent
ratchet steps use $salt = RK$ (the current Root Key), which is a secret, independent input that
provides additional forward-secrecy benefit.  The different salt usage in the handshake vs.\ the
ratchet is therefore intentional and semantically justified.

The first 32 bytes of $OKM$ initialize the Root Key $RK$; the second 32 bytes initialize the
sending Chain Key $CK_s$.
For explicit key confirmation, Alice derives
\[
      K_{conf} = \HKDF\bigl(OKM,\; \mathbf{0}^{32},\;
                            \strlit{StarMesh-Confirm} \,\|\, info,\; 32\bigr)
\]
and computes $tag_A = \HMAC_{\mathrm{SHA3\text{-}256}}(K_{conf},M_0^{core})$, where
$M_0^{core}$ is the handshake transcript excluding the tag itself. Bob verifies $tag_A$ before
accepting the session. This gives Bob explicit confirmation that the sender knows the derived
secret; it is stronger than the previous implicit-only statement but is not by itself mutual
confirmation.

\paragraph{Handshake Message.}
Alice signs the core handshake transcript under her post-quantum identity key to bind
$IK^{DH}_{pk,A}$ to $IK^{DSA}_{pk,A}$, closing the identity-misbinding attack where an
adversary could replace Alice's DH key while retaining her DSA key in $M_0$:
\[
  \sigma_0 \getsr \MLDSA.\Sign\!\bigl(IK^{DSA}_{sk,A},\;
      \strlit{StarMesh-M0} \,\|\, IK^{DH}_{pk,A} \,\|\, EK_{pk,A}
      \,\|\, ct_1 \,\|\, ct_2 \,\|\, tag_A\bigr)
\]
Alice transmits to Bob:
\[
      M_0 = \bigl(IK^{DSA}_{pk,A},\; IK^{DH}_{pk,A},\; EK_{pk,A},\; ct_1,\; ct_2,\;
                 \text{identifier of consumed pre-keys},\; tag_A,\; \sigma_0\bigr)
\]
Bob verifies $\sigma_0$ against $IK^{DSA}_{pk,A}$ before proceeding; a failed
verification causes $M_0$ to be rejected.  Because $\sigma_0$ covers $IK^{DH}_{pk,A}$,
no attacker who does not hold $IK^{DSA}_{sk,A}$ can substitute a different DH key
into $M_0$ and have it accepted.  This check also provides explicit post-quantum
initiator authentication: Bob learns before committing to the session that the sender
holds $IK^{DSA}_{sk,A}$.  Including $IK^{DH}_{pk,A}$ directly in $M_0$ (rather than
requiring Bob to resolve it via a separate DHT bundle lookup) preserves the
asynchronous, offline-completable handshake property: Bob can derive the full session
key from $M_0$ alone, with no live dependency on DHT availability at the moment he
reads his mailbox.

\noindent\textbf{Authentication in $M_0$.}  Alice's identity is explicitly bound to
the handshake through two complementary mechanisms: (i)~the ML-DSA signature
$\sigma_0$ provides explicit post-quantum initiator authentication before the session
key is derived; and (ii)~$tag_A$ provides explicit key confirmation from Alice after
Bob verifies it. Bob's response includes
\[
      tag_B = \HMAC_{\mathrm{SHA3\text{-}256}}\bigl(K_{conf},\; \strlit{Bob} \,\|\, M_0^{core}\bigr),
\]
which Alice verifies before treating the handshake as mutually confirmed.
The computed $SS_{cl}$ includes $DH_1 = \DHop(IK^{DH}_{sk,A}, SPK_{pk,B})$, which is computable
only by the holder of $IK^{DH}_{sk,A}$.  Together with $\sigma_0$, Bob's successful derivation of
the same $OKM$ provides both implicit and explicit authentication of Alice's identity,
analogously to---and stronger than---the implicit authentication property
of standard X3DH \cite{marlinspike_x3dh}.  A replay of $M_0$ with a substituted $EK_{pk,A}$
would fail because the $DH_2/DH_3/DH_4$ components are computed from $EK_{sk,A}$, which the
replayer does not possess.

Bob uses the $IK^{DH}_{pk,A}$ included in $M_0$ together with his own $SPK_{sk,B}$ to recompute
$DH_1$, decapsulates $ct_1, ct_2$ using the corresponding secret keys, recomputes
$SS_{\text{hybrid}}$, and derives the same $OKM$, completing the handshake.

\subsection{Ephemeral PQ Double Ratchet}
\label{sec:ratchet}

Following handshake completion, both parties enter the PQ Double Ratchet.  The state machine
extends the classical Signal Double Ratchet \cite{marlinspike_ratchet} and its generic KEM-based
modularization by Alwen, Coretti, and Dodis \cite{alwen2019doubleratchet} by interleaving ML-KEM
epochs with X25519 DH ratchet steps.

\subsubsection{Ratchet State}

Each node maintains a session state $\mathcal{S}$:
\begin{itemize}
  \item $RK \in \bits^{32}$: Root Key.
  \item $EP \in \bits^{32}$: Synchronized entropy pool, initialized from $RK$ and updated only
        with a successful PQ shared secret.
  \item $CK_s, CK_r \in \bits^{32}$: Sending and Receiving Chain Keys.
  \item $DH^{loc}_{sk}, DH^{rem}_{pk}$: Current local X25519 secret key and remote public key.
  \item $N_s, N_r \in \mathbb{N}$: Send and receive message counters.
  \item $PQ^{loc}_{sk}, PQ^{loc}_{pk}$: Current local ephemeral ML-KEM keypair (may be $\bot$).
  \item $PQ^{outstanding}$: Bounded map from authenticated KEM identifiers to local ephemeral
        ML-KEM secret keys and their send epochs.
  \item $PQ^{pending}$: Bounded map from authenticated KEM identifiers to peer ciphertexts
        awaiting decapsulation.
  \item $PQ^{retired}$: Set of completed or expired KEM identifiers, used for replay rejection.
  \item $\mathcal{K}_{skipped}$: Cache of skipped message keys, bounded at capacity 1000.
  \item $\mathsf{pq\_step\_counter} \in \{0, \ldots, \Delta\}$: Countdown to the next mandatory
        PQ ratchet step, with $\Delta = 50$ (matching Apple's PQ3 cadence \cite{imessage_pq3}).
\end{itemize}

\subsubsection{Symmetric Ratchet, Message Framing, and AEAD Header Authentication}
\label{sec:framing}

Each transmitted message consists of an unencrypted plaintext header $h$ and an AEAD ciphertext $c$:
\[
  m_{\mathrm{wire}} = (h,\; c).
\]
The header binds the session context, ratcheting parameters, and optional asymmetric ratchet extensions:
\[
  h = \bigl(\mathsf{sid},\; DH^{loc}_{pk},\; N_s,\; PN_s,\; \mathsf{flags},\; \mathsf{ext}\bigr),
\]
where $\mathsf{sid}$ is the 32-byte session identifier, $DH^{loc}_{pk}$ is the sender's current classical DH ratchet public key (32 bytes), $N_s$ is the 32-bit message sequence number in the active sending chain, $PN_s$ is the 32-bit length of the previous sending chain (enabling the receiver to skip keys from past epochs upon a ratchet advance), $\mathsf{flags}$ is an 8-bit bitmask indicating asymmetric extension types, and $\mathsf{ext}$ contains optional KEM update payloads (such as $(kem\_id, PQ_{pk}, \sigma_{\mathrm{init}})$ or $(kem\_id, ct, \sigma_{\mathrm{resp}})$ during PQ ratchet rounds).

To encrypt message $i$ in the current sending chain:
\begin{align*}
  MK_i \| CK_s' &= \mathsf{BLAKE3\text{-}KDF}(CK_s, \strlit{StarMesh-MK}) \\
  CK_s &\leftarrow CK_s' \quad (\text{then zeroize previous } CK_s) \\
  N_s &\leftarrow N_s + 1
\end{align*}
The header $h$ is strictly authenticated as Associated Data in AES-256-GCM:
\[
  AD_m \coloneqq \strlit{StarMesh-Header-v1} \,\|\, \flen{h} \,\|\, h,
\]
and the plaintext message $m$ is encrypted as
\[
  c \getsr \mathsf{AES\text{-}256\text{-}GCM}\text{-}\mathsf{Enc}\bigl(MK_i,\; \mathsf{nonce} = N_s^{32} \,\|\, \mathbf{0}^{64},\; AD_m,\; m\bigr),
\]
where $N_s^{32}$ is the 4-byte big-endian encoding of the 32-bit send counter $N_s$, and
$\mathbf{0}^{64}$ is 8 zero bytes, together forming a 12-byte (96-bit) nonce as required by
AES-256-GCM.  The 32-bit counter field is byte-aligned and caps a single chain at
$2^{32}-1 \approx 4.3 \times 10^9$ messages before nonce reuse; in practice, chains are
replaced by DH ratchet steps and PQ ratchet steps well before this bound, but the limit
is stated here as a deliberate design choice rather than an implementation artifact.
Authenticating $h$ in $AD_m$ guarantees that any tampering with sequence counters, session identifiers,
or attached KEM update records causes an immediate GCM authentication failure upon decryption,
preventing state desynchronization attacks before live state is modified.
$MK_i$ is zeroized immediately after use. We instantiate the symmetric ratchet using BLAKE3-KDF rather than HKDF-SHA3-256 due to the high frequency of symmetric updates (triggered per message). BLAKE3's tree-hashing structure yields significantly lower latency and power consumption on resource-constrained devices, while natively supporting secure domain separation.

\subsubsection{DH Ratchet Step}

When Alice sends after receiving a message from Bob (i.e., when $DH^{rem}_{pk}$ has been
updated), a DH ratchet step is triggered:
\[
  DH_{\mathrm{new}} = \DHop(DH^{loc}_{sk},\; DH^{rem}_{pk})
\]
\[
  RK,\; CK_s = \HKDF\!\left(ikm = DH_{\mathrm{new}},\; salt = RK,\;
                             info = \strlit{StarMesh-RK},\; \ell = 64\right)
\]
Alice generates a new $DH^{loc}_{sk}$ and zeroizes the previous one.  The new $DH^{loc}_{pk}$
is attached to the next outgoing message.

\subsubsection{PQ Ratchet Step}
\label{sec:pqratchet}

The PQ ratchet step is triggered when $\mathsf{pq\_step\_counter} = 0$ or on the first message
of a new session.  The step is \emph{role-agnostic}: either party (call them the
\emph{PQ-initiator} and the \emph{PQ-responder}) may trigger it when their counter expires.
The party whose counter first reaches zero becomes the PQ-initiator for that round.
Because state compromise is silent and undetectable by either communicating party, an endpoint
cannot know when a compromise has occurred to dynamically request recovery.  If updates relied
solely on symmetric chain keys in the steady state, an adversary in possession of compromised
symmetric ratchet state could inject an unsigned or symmetrically authenticated update, defeating
post-compromise healing.  Consequently, to satisfy Theorem~\ref{thm:single-update-pcs},
\emph{every} periodic post-quantum ratchet update mandates asymmetric mutual authentication via ML-DSA-65
(\emph{UpdateAuth}) on both the public key proposal and the ciphertext response:

\begin{enumerate}
  \item \textbf{Key Generation and Signing (PQ-initiator):} The PQ-initiator generates a fresh ML-KEM keypair
        $(PQ^{loc}_{sk}, PQ^{loc}_{pk}) \getsr \MLKEM.\KeyGen(1^\lambda)$, allocates an
        identifier $kem\_id$, inserts the pair into $PQ^{outstanding}$, and computes the update signature:
        \begin{align*}
          m_{\mathrm{init}} &\coloneqq \strlit{UpdateAuth-Init} \,\|\, sid \,\|\, kem\_id \,\|\, PQ^{loc}_{pk} \,\|\, epoch \,\|\, prev, \\
          \sigma_{\mathrm{init}} &\getsr \MLDSA.\Sign\bigl(IK^{DSA}_{sk,\mathrm{init}},\, m_{\mathrm{init}}\bigr).
        \end{align*}
        The initiator attaches $(kem\_id, PQ^{loc}_{pk}, \sigma_{\mathrm{init}})$ to the outgoing message.
  \item \textbf{Verification, Encapsulation, and Responder Advance (PQ-responder):}
      Upon receiving the message, the PQ-responder looks up $kem\_id$, rejects duplicate or retired
      identifiers, and verifies $\sigma_{\mathrm{init}}$:
      \[
        \MLDSA.\Verify\bigl(IK^{DSA}_{pk,\mathrm{init}},\, m_{\mathrm{init}},\, \sigma_{\mathrm{init}}\bigr) \stackrel{?}{=} 1.
      \]
      If verification fails, the payload is rejected.  If valid, the responder computes
      $(PQ^{pending}_{ct}, SS_{PQ}) \getsr \MLKEM.\Encaps(PQ^{loc}_{pk})$ and signs the canonical bound response:
      \begin{align*}
        m_{\mathrm{resp}} &\coloneqq \strlit{UpdateAuth-Resp} \,\|\, sid \,\|\, kem\_id \,\|\, PQ^{loc}_{pk} \,\|\, PQ^{pending}_{ct} \,\|\, epoch \,\|\, prev, \\
        \sigma_{\mathrm{resp}} &\getsr \MLDSA.\Sign\bigl(IK^{DSA}_{sk,\mathrm{resp}},\, m_{\mathrm{resp}}\bigr).
      \end{align*}
      The responder then executes the post-quantum root and directional chain update:
      \begin{align*}
        EP' &\gets \HKDF\bigl(SS_{PQ},\; EP,\;
                          \strlit{StarMesh-EntropyPool} \,\|\, PQ^{pending}_{ct},\; 32\bigr), \\
        (RK',\, \vec{CK}) &\gets \HKDF\bigl(SS_{PQ},\; EP',\;
                                              \strlit{StarMesh-PQ-RK},\; 96\bigr),
      \end{align*}
      where $\vec{CK} = (CK_{A\to B}, CK_{B\to A})$.
      The responder synchronizes its directional chains and root key:
      \[
        RK \leftarrow RK', \quad CK_r \leftarrow CK_{A\to B}, \quad CK_s \leftarrow CK_{B\to A}, \quad EP \leftarrow EP',
      \]
      zeroizes $SS_{PQ}$ and old root/chain keys, and resets $\mathsf{pq\_step\_counter} \leftarrow \Delta$.
      The responder attaches $(kem\_id, PQ^{pending}_{ct}, \sigma_{\mathrm{resp}})$ to its reply.
  \item \textbf{Response Verification and Initiator Advance (PQ-initiator):} Upon receiving the reply, the
      PQ-initiator looks up $kem\_id$ in $PQ^{outstanding}$ and verifies $\sigma_{\mathrm{resp}}$:
      \[
        \MLDSA.\Verify\bigl(IK^{DSA}_{pk,\mathrm{resp}},\, m_{\mathrm{resp}},\, \sigma_{\mathrm{resp}}\bigr) \stackrel{?}{=} 1.
      \]
      If invalid, the reply is dropped.  If valid, the initiator decapsulates
      \[
        SS_{PQ} = \MLKEM.\Decaps\bigl(PQ^{loc}_{sk},\, PQ^{pending}_{ct}\bigr),
      \]
      and computes the identical entropy pool and 96-byte derivation:
      \begin{align*}
        EP' &\gets \HKDF\bigl(SS_{PQ},\; EP,\;
                          \strlit{StarMesh-EntropyPool} \,\|\, PQ^{pending}_{ct},\; 32\bigr), \\
        (RK',\, \vec{CK}) &\gets \HKDF\bigl(SS_{PQ},\; EP',\;
                                              \strlit{StarMesh-PQ-RK},\; 96\bigr).
      \end{align*}
      The initiator synchronizes its directional chains and root key:
      \[
        RK \leftarrow RK', \quad CK_s \leftarrow CK_{A\to B}, \quad CK_r \leftarrow CK_{B\to A}, \quad EP \leftarrow EP',
      \]
      applies completed updates in increasing authenticated sequence, retires $kem\_id$,
      zeroizes $PQ^{loc}_{sk}$, $SS_{PQ}$, and old keys, and resets $\mathsf{pq\_step\_counter} \leftarrow \Delta$.
      A duplicate response never causes a second root-key update; a timeout retires the identifier without changing
      the root key and requires a fresh keypair on retry.  The complete concurrent-buffer
      state machine is specified in Appendix~\ref{sec:appendix-statemachine}.
\end{enumerate}

\begin{remark}[Symmetry and Concurrent PQ Steps]
\label{rem:concurrent}
Both parties maintain independent $\mathsf{pq\_step\_counter}$ values.  It is possible for
both counters to reach zero concurrently.  In this case both parties independently generate a
fresh $PQ^{loc}_{pk}$ and act as simultaneous PQ-initiators for separate round-trips that
proceed in parallel.  Each completes independently; the result is two consecutive PQ-induced
root-key updates, which only strengthens the PCS guarantee.
\end{remark}

\begin{remark}[Pre-Recovery Exposure Window and Justification of $\Delta = 50$ (Informal)]
\label{rem:delta}
The parameter $\Delta$ governs the maximal interval between PQ ratchet steps.
In normal execution between PQ updates, intermediate message confidentiality against a recording
CRQC is preserved because the root key $RK$ incorporates post-quantum secrecy from the preceding
handshake or prior PQ ratchet updates, and each classical DH ratchet update evaluates
$\HKDF(DH_{\mathrm{new}}, salt = RK, \dots)$.  A recording quantum adversary who captures only public
ephemeral keys on the wire cannot compute the derived chain keys without knowledge of the secret $RK$.

\textbf{Post-compromise exposure bound (informal).}  Exposure arises when an adversary compromises
an endpoint's live session state at time $t_{comp}$, thereby learning the live root key $RK$.  Against
an adversary possessing this compromised state \emph{and} quantum capability (a CRQC), intermediate
classical X25519 DH ratchet steps no longer provide healing: the adversary computes
$DH_{\mathrm{new}}$ by solving the discrete logarithm of the peer's public ephemeral key, and
evaluates $\HKDF$ with the known $RK$ to track subsequent chain keys.  Consequently, healing cannot
occur through classical DH steps alone once $RK$ is known; the adversary recovers all messages sent
from the point of state compromise until a fresh post-quantum ratchet round-trip \emph{completes}.

The pre-recovery exposure window is thus bounded by the number of messages sent before:
(i)~an endpoint emits a fresh $PQ^{loc}_{pk}$ proposal (delayed by up to $\Delta$ messages as the
ratchet counter decrements), plus (ii)~the network round-trip time required for the peer's
authenticated KEM ciphertext reply to arrive and be accepted.  Crucially, if the peer is offline or
network packets are delayed or dropped, this window is unbounded in time until an authenticated
round-trip successfully completes.  Only after the full round-trip completes does the session
re-enter the secure, fresh state governed by Theorem~\ref{thm:single-update-pcs}.

Message keys from DH epochs that have already been deleted (enforced deletion schedule,
Section~\ref{sec:deletion}) are \emph{not} recoverable: their chain keys were zeroized
before the capture event.  The exposure is therefore strictly bounded to messages sent \emph{during}
the post-compromise window, not the entire session history.

Our choice of $\Delta = 50$ follows the periodic post-quantum ratchet cadence established by Apple's
PQ3 protocol \cite{imessage_pq3} (surveyed in \cite{dodis2025tripleratchet}).  This choice amortises
the transmission of post-quantum key material across 50 messages while providing a concrete,
tunable baseline on the pre-recovery exposure count.  Operators with higher security requirements
should reduce $\Delta$; those in high-latency or asynchronous environments must also account for
round-trip time and peer availability when estimating the actual exposure window.
\end{remark}

\subsubsection{Out-of-Order Message Handling: Max-Skip Bound and Staged Commit}
\label{sec:outoforder}

When network delivery reorders messages, a message may arrive with sequence counter $N > N_r$:
\begin{enumerate}
  \item \textbf{Max-Skip Bound:} To protect against denial-of-service and memory exhaustion attacks
        from unauthenticated forged counters, the receiver enforces a strict skip threshold
        $N_{\mathrm{max\_skip}} = 1{,}000$.  If $N - N_r > N_{\mathrm{max\_skip}}$, the packet is
        immediately rejected and discarded without evaluating any cryptographic operations or advancing state.
  \item \textbf{Staged Key Derivation (Commit-After-Authentication):} Rather than immediately advancing
        the live receiving chain key $CK_r$, the receiver derives candidate skipped keys into a transient,
        isolated scratch buffer:
        \begin{align*}
          MK_j \,\|\, CK_{\mathrm{temp}} &= \mathsf{BLAKE3\text{-}KDF}(CK_{\mathrm{temp}}, \strlit{StarMesh-MK}), \; j \in [N_r, N-1], \\
          MK_N \,\|\, CK_{\mathrm{target}} &= \mathsf{BLAKE3\text{-}KDF}(CK_{\mathrm{temp}}, \strlit{StarMesh-MK}).
        \end{align*}
        The receiver attempts AEAD authentication and decryption using the target candidate key $MK_N$:
        \[
          m \gets \mathsf{AES\text{-}256\text{-}GCM}\text{-}\mathsf{Dec}\bigl(MK_N,\; \mathsf{nonce} = N^{32} \,\|\, \mathbf{0}^{64},\; AD_m,\; c\bigr).
        \]
  \item \textbf{Conditional State Commit:}
        \begin{itemize}
          \item \textit{If decryption and tag verification succeed:} The receiver commits the staged updates:
                the skipped keys $\{MK_{N_r}, \dots, MK_{N-1}\}$ are committed to the bounded skipped-key cache
                $\mathcal{K}_{skipped}$ (capacity 1{,}000, oldest keys zeroized upon overflow), the receiving
                counter advances $N_r \leftarrow N + 1$, and the live chain key updates $CK_r \leftarrow CK_{\mathrm{target}}$.
                $MK_N$ and intermediate scratch memory are zeroized immediately.
          \item \textit{If tag verification fails:} The candidate scratch buffer (including all staged keys and
                $CK_{\mathrm{target}}$) is instantly zeroized and destroyed.  Live state ($CK_r$, $N_r$, and
                $\mathcal{K}_{skipped}$) remains strictly unmodified, ensuring an attacker cannot desynchronize
                or destroy live receiver chains by injecting invalid packets with elevated sequence numbers.
        \end{itemize}
  \item \textbf{Delayed Delivery:} When a delayed message with sequence number $N < N_r$ arrives, the receiver
        looks up $MK_N$ in $\mathcal{K}_{skipped}$.  If present, it verifies and decrypts the payload, extracts $m$,
        and immediately zeroizes and deletes $MK_N$ from the cache.  If $MK_N$ is absent (already consumed or evicted),
        the packet is permanently undecryptable and dropped.
\end{enumerate}

\subsubsection{Deletion Schedule}
\label{sec:deletion}

The following deletion schedule is mandatory and forms the basis of the forward secrecy and
PCS proof sketches.  Its enforcement is an \emph{operational assumption} (see
Section~\ref{sec:assumptions}); the protocol logic specifies the schedule but cannot itself
verify that an implementation honours it.

\begin{itemize}
  \item \textbf{Message Keys ($MK_i$):} Zeroized immediately after a single AES-GCM
        encryption or decryption operation.
  \item \textbf{Chain Keys ($CK_s$, $CK_r$):} Zeroized immediately upon derivation of the
        subsequent chain key.
  \item \textbf{Ephemeral X25519 Secrets ($DH^{loc}_{sk}$):} Zeroized immediately upon
        generation of the next local DH keypair.
  \item \textbf{Ephemeral ML-KEM Secrets:} Each secret in $PQ^{outstanding}$ is zeroized
        immediately after its matching ciphertext is decapsulated; outstanding entries are
        bounded, authenticated, and retired independently.
  \item \textbf{One-Time Pre-Key Secrets:} Zeroized immediately after use in the handshake.
  \item \textbf{Skipped Keys:} Zeroized either upon successful use or upon eviction from the
        bounded cache.
\end{itemize}

\subsection{Prototype Implementations}
\label{sec:poc}

To validate the correctness of the cryptographic state machine described in this section, we
developed two proof-of-concept implementations available in the open-source repository
accompanying this paper\footnote{\url{https://github.com/Samin-yasar/star-mesh} (Apache-2.0 License).}:

\begin{enumerate}
  \item \textbf{Python Prototype} (\texttt{poc/python/poc.py}): A dependency-free Python~3
        implementation that simulates the commutative key exchange and the state transitions of
        the hybrid Double Ratchet.  DH operations are modeled via modular exponentiation over a
        standard 1024-bit MODP prime (RFC~2409 Group~2) to preserve the algebraic commutativity
        property of Diffie--Hellman, and ML-KEM-768 is simulated while preserving the
        IND-CCA2 encapsulate/decapsulate API contract.  The Python prototype successfully
        verifies OKM convergence between initiator and responder.

  \item \textbf{Rust Prototype} (\texttt{poc/rust/src/main.rs}): A high-fidelity implementation
        using production-ready RustCrypto libraries:
        \begin{itemize}
          \item \texttt{ml-kem}~(v0.3) for FIPS~203 ML-KEM-768 \cite{nist_fips203}.
          \item \texttt{ml-dsa}~(v0.1.1) for FIPS~204 ML-DSA-65 \cite{nist_fips204}, providing
                the mandatory mutual update signatures ($\sigma_{\mathrm{init}}$ and $\sigma_{\mathrm{resp}}$).
          \item \texttt{x25519-dalek}~(v2.0) for RFC~7748 X25519 \cite{rfc7748}.
          \item \texttt{aes-gcm}~(v0.10) for AES-256-GCM authenticated payload encryption with header binding.
          \item \texttt{blake3}~(v1.0) and \texttt{hkdf}~(v0.12) / \texttt{sha3}~(v0.10) for
                BLAKE3-KDF and HKDF-SHA3-256.
          \item \texttt{zeroize}~(v1.0) for memory shredding, directly enforcing the deletion
                schedule specified above.
        \end{itemize}
        The implementation requires a modern Rust compiler ($\ge 1.85$, with \texttt{rust-version = "1.85"}
        enforced in \texttt{Cargo.toml}) due to upstream cryptographic crates supporting the 2024 edition ecosystem.
\end{enumerate}

Both prototypes execute the full hybrid PQ-X3DH handshake, verify OKM convergence, advance the
symmetric and post-quantum ratchet steps, and confirm root-key convergence after a PQ ratchet
round-trip, consistent with the PCS healing mechanism argued in Section~\ref{sec:pcsproof}.

\paragraph{Formal Symbolic Models.}
The repository also includes two ProVerif~\cite{proverif} models providing machine-checked
symbolic verification in the Dolev-Yao attacker model:
\begin{enumerate}
  \item \textbf{\texttt{formal/pq\_x3dh.pv}} (Unbounded Handshake Model):
        Three queries over unbounded, interleaved sessions:
        \begin{itemize}
          \item \textit{PQ-FS}:
                \texttt{not attacker(sess\_key\_witness[])} $\checkmark$
          \item \textit{MITM resistance}:
                \texttt{event(AliceFinished)} $\implies$
                \texttt{event(BobPublished)} $\checkmark$
          \item \textit{Initiator auth}:
                \texttt{event(BobAcceptedM0)} $\implies$
                \texttt{event(AliceStarted)} $\checkmark$
        \end{itemize}
        The third query machine-checks that $IK^{DH}_{pk,A}$ is bound to
        $IK^{DSA}_{pk,A}$ via $\sigma_0$: a DH-key-substitution attacker
        cannot produce a valid $\sigma_0$ without $IK^{DSA}_{sk,A}$.
  \item \textbf{\texttt{formal/ratchet.pv}} (PQ Double Ratchet Model): Verifies four queries
        over a bounded execution with state compromise, a PQ ratchet round-trip,
        and skipped-key cache modeling:
        \begin{itemize}
          \item Pre-compromise forward secrecy:
                \texttt{not} \texttt{attacker(w\_pre\_comp[])}.
          \item PCS healing after one PQ round-trip:
                \texttt{not} \texttt{attacker(w\_post\_heal[])}.
          \item Skipped-key cache caveat (Corollary~\ref{cor:pcs}, Caveat~2):\\
                \texttt{not attacker(w\_skipped\_pre[])} is false
                (the key remains exposed post-healing).
          \item Post-heal message agreement:
                \texttt{event(BobReceivedPostHeal(m))} $\implies$ \linebreak
                \null\hfill\texttt{event(AliceSentPostHeal(m))}.
        \end{itemize}
        We clarify that this symbolic model covers the unsigned ratchet logic only (validating symmetric chain advancement, KEM shared secret derivation, and secret erasure transitions); it does not model the mutual ML-DSA-65 update signatures or an unrevealed identity key required by Theorem~\ref{thm:single-update-pcs}.
\end{enumerate}
Both models can be reproduced by running \texttt{make verify} in the repository root
(requires ProVerif 2.04+ installed via OPAM).

\subsection{Cryptographic Assumptions}
\label{sec:assumptions}

We state all assumptions explicitly; proof sketches reference only assumptions listed here.

\begin{assumption}[Module-LWE Hardness and ML-KEM Security]
\label{asm:mlwe}
The Module-LWE problem with parameters $n = 256$, $k = 3$ (ML-KEM-768 parameters) is hard for
all QPT adversaries \cite{langlois2015mlwe}.  Under this assumption, ML-KEM-768 is
IND-CCA2 secure under the standardized construction \cite{nist_fips203}.
\end{assumption}

\begin{assumption}[EUF-CMA Security of ML-DSA-65]
\label{asm:mldsa}
The ML-DSA-65 signature scheme \cite{nist_fips204} is Existentially Unforgeable under Adaptive
Chosen-Message Attacks (EUF-CMA) for all QPT adversaries.
\end{assumption}

\begin{assumption}[Computational Diffie--Hellman on Curve25519]
\label{asm:cdh}
The Computational Diffie--Hellman (CDH) problem on Curve25519 is hard for all classical PPT
adversaries (and QPT adversaries prior to CRQC compromise of classical identity keys).
\end{assumption}

\begin{assumption}[HKDF as Dual-PRF and Extractor]
\label{asm:hkdf}
HKDF-SHA3-256 is modeled as a two-stage extract-then-expand PRF and computational extractor
in the standard model, following Krawczyk \cite{krawczyk2010hkdf}:
\begin{enumerate}
  \item \textbf{Extraction (Dual-PRF property):} $\mathsf{HMAC}_{salt}(ikm)$ produces a pseudorandom
        key $\mathsf{PRK}$ whenever either (a)~$salt$ is a secret, uniform key, or (b)~$salt$ is a fixed
        public string (including $salt = \mathbf{0}^{32}$) and $ikm$ contains at least one computationally
        uniform secret component $u$ independent of known components $p$ (the one-uniform-component
        extractor property).
  \item \textbf{Expansion (PRF property):} $\mathsf{HKDF\text{-}Expand}(\mathsf{PRK}, info, \ell)$ is a
        standard PRF keyed by $\mathsf{PRK}$.
\end{enumerate}
All proof sketches invoking the pseudorandomness of derived keys rely on this assumption.  We do
\emph{not} model SHA3-256 as a random oracle; standard-model PRF and dual-PRF extraction are sufficient
for our reductions.
\end{assumption}

\begin{assumption}[BLAKE3-KDF as PRF]
\label{asm:blake3}
The keyed hashing mode of BLAKE3 \cite{blake3}, used to derive message keys ($MK_i$) and
next chain keys ($CK'_s$) from the current chain key, is modeled as a pseudorandom function
(PRF) in the standard model.  Concretely, $\mathsf{BLAKE3\text{-}KDF}(k, \mathit{ctx})$ with
keyed-hash domain separation is PRF-secure: for a uniform key $k$, the outputs are
indistinguishable from uniform bitstrings by any PPT adversary who does not know $k$.
This assumption is required for the pseudorandomness of $MK_i$ used in the AES-256-GCM
encryption step, and is load-bearing for the per-message confidentiality claims that underlie
both Security Claim~\ref{thm:pqfs} and Theorem~\ref{thm:single-update-pcs}.  The PRF security of
BLAKE3's keyed hash mode follows from its design analysis \cite{blake3} and is consistent
with standard-model PRF modeling of keyed sponge and tree-hash constructions.
\end{assumption}

\begin{assumption}[Dual-PRF / One-Uniform-Component Extractor Security — Handshake and Ratchet Cases]
\label{asm:kdf-hi}
HKDF-SHA3-256 satisfies the partial-uniformity KDF game of Definition~\ref{def:kdf-hi}.
We state the assumption separately for the two distinct contexts where it is invoked, detailing
which component is uniform in each reduction branch.

\medskip\noindent
\textbf{Case 1: Handshake (Public Salt, Concatenated Hybrid IKM).}
The input key material fed to HKDF in the initial handshake is
\[
  ikm = \hexlit{0xFF} \,\|\, SS_{cl} \,\|\, SS_{PQ1} \,\|\, SS_{PQ2}
\]
(or in the SPK-only fallback, $ikm = \hexlit{0xFF} \,\|\, SS_{cl} \,\|\, SS_{PQ1}$).
The salt is fixed and public ($salt = \mathbf{0}^{32}$), and the context string $info$ is the
length-prefixed public transcript binder ($AD \,\|\, \flen{EK_{pk,A}} \,\|\, EK_{pk,A} \,\|\, \flen{ct_1} \,\|\, ct_1 \,\|\, \flen{ct_2} \,\|\, ct_2$).
Under the one-uniform-component extractor assumption, the extracted PRK and derived output key material
$OKM$ are computationally indistinguishable from uniform provided that at least one constituent shared
secret in $ikm$ is computationally uniform and independent of the remaining components.
This covers three distinct reduction branches:
\begin{itemize}
  \item \textbf{Branch 1a (Post-Quantum FS with OTPK — Primary Reduction):}
        The adversary has compromised classical long-term identity keys (or possesses a CRQC that
        solves classical discrete logarithms); hence $SS_{cl}$ is known.  The semi-static secret
        $SS_{PQ1}$ may also be known to the adversary.  The reduction embeds the IND-CCA2 challenge
        into the fresh one-time pre-key $PQ\_OTPK_{pk,B}$ ($ct_2$), replacing $SS_{PQ2}$ with a
        computationally uniform random string $u \getsr \bits^{32}$.  Here:
        \begin{align*}
          u &= SS_{PQ2} \quad \text{(uniform, hidden from $\mathcal{A}$)}, \\
          p &= (\hexlit{0xFF},\, SS_{cl},\, SS_{PQ1}) \quad \text{(known or adversarial)}.
        \end{align*}
        The one-uniform-component extractor property guarantees that $OKM$ is pseudorandom, with
        distinguishing advantage bounded by $\Adv^{\mathrm{hi}}_{\mathrm{KDF}}(\mathcal{B}_{\mathrm{KDF}})$.
  \item \textbf{Branch 1b (Post-Quantum FS in SPK-Only Fallback):}
        When no OTPK is available in Bob's bundle (Remark~\ref{rem:spkonly}), the handshake omits
        $ct_2$ and uses $ikm = \hexlit{0xFF} \,\|\, SS_{cl} \,\|\, SS_{PQ1}$.  The reduction embeds
        the IND-CCA2 challenge into $PQ\_SPK_{pk,B}$ ($ct_1$).  Here:
        \begin{align*}
          u &= SS_{PQ1} \quad \text{(uniform, hidden from $\mathcal{A}$)}, \\
          p &= (\hexlit{0xFF},\, SS_{cl}) \quad \text{(known or adversarial)}.
        \end{align*}
        The one-uniform-component extractor property guarantees pseudorandomness of $OKM$ at the
        granularity of $PQ\_SPK$ rotation epochs.
  \item \textbf{Branch 1c (Classical Forward Secrecy / Pre-Quantum Adversary):}
        The adversary is pre-quantum (no CRQC), but the post-quantum KEMs are unanalyzed or broken.
        Under the CDH assumption on Curve25519 (Assumption~\ref{asm:cdh}), the ephemeral DH secret
        $SS_{cl}$ is computationally uniform and independent of the pre-keys.  Here:
        \begin{align*}
          u &= SS_{cl} \quad \text{(uniform, hidden from $\mathcal{A}$)}, \\
          p &= (\hexlit{0xFF},\, SS_{PQ1},\, SS_{PQ2}) \quad \text{(known or adversarial)}.
        \end{align*}
        The one-uniform-component extractor property guarantees classical forward secrecy against
        passive and active classical adversaries.
\end{itemize}

\medskip\noindent
\textbf{Case 2: Ratchet (Secret Salt, Pure KEM Secret).}
In the post-quantum ratchet update (Section~\ref{sec:pqratchet}), the IKM fed to HKDF contains no
known classical or public components:
\[
  ikm = SS_{PQ},
\]
where $SS_{PQ}$ is the ML-KEM shared secret from the mutually authenticated update.
Here $p = \varepsilon$ (empty prefix) and $u = SS_{PQ}$:
\begin{itemize}
  \item \textbf{Reduction branch (PCS Theorem~\ref{thm:single-update-pcs}):}
        In the IND-CCA2 reduction for ML-KEM, the challenge shared secret replaces $SS_{PQ}$ with a
        computationally uniform string $u \getsr \bits^{32}$.  Thus the single component
        $ikm = u = SS_{PQ}$ is fully uniform and hidden from the adversary.
  \item \textbf{Salt structure:}
        In the entropy-pool derivation, $salt = EP$ (the live entropy pool from the prior epoch).
        In the root-key and chain-key derivation, $salt = EP'$ (the updated entropy pool).
        Because $EP$ and $EP'$ are derived from prior post-quantum updates and preserved under state
        compression/erasure, $salt$ is a secret, high-entropy string rather than a public value.
  \item \textbf{Domain separation:}
        $info = \strlit{StarMesh-EntropyPool} \,\|\, PQ^{pending}_{ct}$ and
        $info = \strlit{StarMesh-PQ-RK}$ isolate the respective derivations.
\end{itemize}
Because $salt$ is secret and high-entropy, the extraction step operates as a standard PRF keyed by
$salt$ (and benefits additionally from the uniform entropy in $u = SS_{PQ}$).  Even if $salt$ were
exposed, the uniform $u$ alone would suffice under the dual-PRF property.  Consequently, the derived
values $EP'$, $RK$, and $CK_s$ are computationally indistinguishable from independent uniform strings,
with distinguishing advantage $\Adv^{\mathrm{hi}}_{\mathrm{KDF}}(\mathcal{B}_{\mathrm{KDF}})$.
(Similarly, in the classical DH ratchet step of Section~\ref{sec:ratchet}, $ikm = DH_{\mathrm{new}}$ is
uniform under CDH with secret $salt = RK$.)

\medskip\noindent
This formulation ensures that the KDF extraction security is strictly separated from the KEM IND-CCA2
and classical CDH hardness reductions across all protocol phases, avoiding circularity or
double-counting.
\end{assumption}

\begin{assumption}[DHT Availability and Sybil Resistance]
\label{asm:dht}
The Kademlia DHT is available and Sybil-resistant in the sense that no adversary can eclipse
a target user's mailbox.  This is an operational assumption; it is not proven by the protocol
logic.
\end{assumption}

\begin{assumption}[Mixnet Honesty Fraction]
\label{asm:mixnet}
At most a fraction $f < 1/2$ of mix nodes are adversarially controlled, following the Loopix
threat model \cite{loopix}.  This quantifies the trust requirement on the routing overlay.
\end{assumption}

\begin{assumption}[Deletion Schedule Enforcement]
\label{asm:deletion}
The deletion schedule specified in Section~\ref{sec:ratchet} is enforced by the implementation.
In particular, message keys, chain keys, and ephemeral secret keys are zeroized at the times
specified.  This is an operational assumption.
\end{assumption}

\begin{assumption}[RNG Integrity after $t_{rec}$]
\label{asm:rng}
The node's random number generator is not compromised by the adversary for any sampling event
after time $t_{rec}$.  This models a recovered operating environment (clean OS RNG,
side-channel-free execution) following a prior compromise event.  Foundational theory for
extracting usable randomness from imperfect, seed-dependent sources is given by
Dodis et al.\ \cite{dodis2013entropic}; our $\mathcal{O}_{\mathsf{RevealRNG}}$/recovery-time
abstraction is an explicit operational modelling assumption of this work.  If the RNG is
compromised during the PQ ratchet
key generation after $t_{rec}$, PCS is unachievable for that update.
\end{assumption}

\begin{assumption}[Identity Key Isolation across State Compromise]
\label{asm:idkey-isolation}
The endpoint's long-term identity signing key ($IK^{DSA}_{sk}$) resides in an isolated, tamper-resistant
execution environment (such as a hardware security module, secure enclave, or protected operating-system keystore)
and is not exfiltrated during an ephemeral session state compromise.  The corruption oracle
$\mathsf{Corrupt}(P, t)$ returns volatile session memory (ephemeral chain keys, root keys, entropy pool,
pending ciphertexts, and transient keys), but strictly excludes $IK^{DSA}_{sk}$.

This assumption additionally requires \emph{no signing-oracle access during the compromise window}: the
adversary cannot ask the enclave to sign attacker-chosen update transcripts on its behalf while
the session state is exposed.  If the adversary does obtain signing-oracle access during the window,
it can produce a validly signed update that collides with a target transcript, defeating the DSA
reduction; healing would still hold for a passive-after-compromise adversary (one that reads state
but does not obtain signing-oracle access) relying solely on KEM IND-CCA2 and a clean RNG, but
would fail against an active adversary with signing-oracle access.

Post-compromise security holds only if both conditions are met---the identity signing key is not
exfiltrated \emph{and} the adversary cannot query the enclave's signing oracle during the compromise
window.  If either condition fails against an active adversary, an update forging or replay attack
becomes possible and post-compromise recovery cannot be guaranteed.
\end{assumption}

\begin{remark}[Entropy-pool recovery boundary]
\label{rem:entropy-pool}
\textbf{Key point:} the entropy pool provides no additional security unless $SS_{PQ}$ itself is
unknown to the adversary, i.e., unless the fresh ML-KEM keypair was generated with an
uncompromised RNG.

The implementation maintains a synchronized entropy pool $EP$ updated after a successful PQ
ratchet as $EP' = \HKDF(SS_{PQ}, EP,
\strlit{StarMesh-EntropyPool} \| ct, 32)$.  The ciphertext $ct$ appears as public transcript
context for domain separation, not as an entropy source: a known root key concatenated with a
public ciphertext cannot heal a compromised RNG.  If the adversary already knows $SS_{PQ}$
(because it compromised the RNG before the fresh keypair was generated), the pool update is
completely transparent to the adversary.  Recovery therefore depends entirely on whether the
ML-KEM key-generation event at $t_{rec}$ was fresh.  A stronger theorem under partially
subverted RNGs would require an explicit entropy-source model (e.g., following
\cite{dodis2013entropic}) and is left for future work.
\end{remark}

\subsection{Execution Environment and Adversary}

We model execution using a multi-party protocol execution game adapted from
\cite{cohngordon2016,cremers2024ratchet}.  Oracle naming in this paper is normalized to a
single notation ($\calO^{Reveal}$, $\calO^{RevealLTK}$, etc.); it is intended to be
semantically aligned with their state-reveal and long-term-key compromise queries rather than a
verbatim reproduction of prior oracle labels.  Let $\mathcal{P} = \{P_1, \ldots, P_n\}$ be a set
of parties.  Each party $P_i$ may hold multiple sessions; we denote by $\pi^s_i$ the $s$-th
session of party $P_i$.

We evaluate Star-Mesh against a \textbf{quantum-active adversary} $\calA_{\mathrm{quant}}$,
modeled as a non-uniform quantum polynomial-time (QPT) algorithm equipped with a CRQC.
$\calA_{\mathrm{quant}}$ has the following capabilities.

\begin{definition}[Adversarial Oracles]
\label{def:oracles}
The adversary $\calA_{\mathrm{quant}}$ may adaptively query the following oracles:
\begin{itemize}
  \item $\calO^{Send}(i, s, m)$: Delivers, injects, modifies, or drops message $m$ to/from
        session $\pi^s_i$.  $\calA_{\mathrm{quant}}$ has full network control.
  \item $\calO^{Reveal}(i, s)$: Returns the current ratchet state $\mathcal{S}$ of session
        $\pi^s_i$ (simulating device compromise).
  \item $\calO^{RevealLTK}(i)$: Returns the long-term secret keys of party $P_i$.
  \item $\calO^{RevealRNG}(i, t)$: Reveals or controls the output of $P_i$'s random number
        generator at time $t$.  This models a compromised OS RNG, a side-channel attack, or
        any mechanism by which the adversary learns or influences fresh randomness
        \cite{dodis2013entropic}.
  \item $\calO^{Test}(i, s, e)$: Returns either the real epoch-$e$ message key $MK_e$ or a
        uniformly random key; the adversary's goal is to distinguish.
\end{itemize}
\end{definition}

\begin{definition}[Fresh Session Epoch]
\label{def:fresh}
An epoch $e$ of session $\pi^s_i$ is \textbf{fresh} if no $\calO^{Test}$ query has been made
on it, and the adversary's combined query history does not allow derivation of $MK_e$ from
revealed material.  Formally, epoch $e$ is \emph{not fresh} if any of the following hold:
\begin{enumerate}
  \item $\calO^{Reveal}(i, s)$ was queried after the last DH ratchet step preceding epoch $e$,
        \emph{and} $\calO^{Reveal}(j, s')$ was queried for the corresponding peer session
        $\pi^{s'}_j$.
  \item $\calO^{RevealLTK}(i)$ was queried \emph{and} all one-time pre-key secrets of
        \emph{Bob's} bundle used in session $\pi^s_i$ were previously revealed via
        $\calO^{Reveal}$.
  \item $\calO^{RevealRNG}(i, t)$ was queried for any time $t$ at which a fresh ephemeral
        secret (ephemeral DH key, ephemeral ML-KEM keypair, or one-time pre-key) used to derive
        $MK_e$ was sampled.
\end{enumerate}
\end{definition}

\begin{remark}
Condition~3 integrates RNG compromise into the freshness definition, replacing the ad-hoc RNG
boundary used in prior formulations.  It ensures that the PCS game (Definition~\ref{def:pcs})
does not need to re-define the RNG boundary separately: any session whose PQ ratchet keypair
was sampled during a compromised-RNG window is simply not fresh for the affected epochs.
\end{remark}

\subsection{Post-Quantum Forward Secrecy (PQ-FS) Game}

\begin{definition}[PQ-FS Security]
\label{def:pqfs}
Consider the following game $\PGame^{\mathrm{PQ\text{-}FS}}_{\calA}(\lambda)$:
\begin{enumerate}
  \item The challenger runs all honest party key generation and initializes the DHT.
  \item $\calA_{\mathrm{quant}}$ adaptively issues $\calO^{Send}$, $\calO^{Reveal}$,
        $\calO^{RevealLTK}$, and $\calO^{RevealRNG}$ queries.
  \item $\calA_{\mathrm{quant}}$ selects a target session $\pi^s_i$ and a target epoch $e$
        that is fresh per Definition~\ref{def:fresh}.  It additionally requires that $e$
        precedes the time of any $\calO^{Reveal}$ query on $\pi^s_i$.
  \item The challenger samples $b \getsr \bits$.  If $b = 0$, it returns $MK_e$; if $b = 1$,
        it returns $r \getsr \bits^{256}$.
  \item $\calA_{\mathrm{quant}}$ outputs a guess $b'$.
\end{enumerate}
The advantage is $\Adv^{\mathrm{PQ\text{-}FS}}_{\mathrm{SM}}(\calA) \coloneqq
|\Pr[b' = b] - \tfrac{1}{2}|$.  The protocol achieves \textbf{PQ-FS} if this advantage is
negligible for all QPT $\calA_{\mathrm{quant}}$.
\end{definition}

\subsection{Post-Compromise Security (PCS) Game}

\begin{definition}[PCS Security]
\label{def:pcs}
Consider the following game $\PGame^{\mathrm{PCS}}_{\calA}(\lambda)$:
\begin{enumerate}
  \item The challenger initializes all sessions.  $\calA_{\mathrm{quant}}$ may issue arbitrary
        oracle queries.
  \item $\calA_{\mathrm{quant}}$ issues $\calO^{Reveal}(i, s)$ at time $t_{comp}$, obtaining
        the full ratchet state.
  \item $\calO^{RevealRNG}(i, t)$ may be queried at any time $t \leq t_{rec}$ for some
        recovery time $t_{rec} \geq t_{comp}$.  After $t_{rec}$, by Assumption~\ref{asm:rng},
        the RNG is clean; freshness Condition~3 (Definition~\ref{def:fresh}) therefore does not
        apply to keys sampled after $t_{rec}$.
  \item After time $t_{rec}$, at least one complete authenticated PQ buffer round-trip is
        executed: Alice samples a fresh keypair, inserts it under a new $kem\_id$, sends the
        public key to Bob, Bob returns a ciphertext carrying the same identifier, and Alice
        decapsulates it, retires the identifier, and zeroizes the matching secret.
  \item $\calA_{\mathrm{quant}}$ selects a target epoch $e'$ in session $\pi^s_i$ satisfying
        (a)~$e'$ occurs after the round-trip of step~4 completes; (b)~the chain key for epoch
        $e'$ is derived \emph{after} the round-trip (not from a pre-compromise chain key); and
        (c)~the message key $MK_{e'}$ is not in $\mathcal{K}_{skipped}$ from before $t_{rec}$.
        The challenger responds with a Test oracle call.
  \item $\calA_{\mathrm{quant}}$ outputs a guess $b'$.
\end{enumerate}
The protocol achieves \textbf{PCS} if $\Adv^{\mathrm{PCS}}_{\mathrm{SM}}(\calA) \in
\negl(\lambda)$ for all QPT $\calA_{\mathrm{quant}}$.
\end{definition}

\subsection{A Single-Update Recovery Theorem}
\label{sec:single-update-theorem}

The following theorem deliberately targets one authenticated recovery update rather than the
complete decentralized protocol.  It makes explicit a condition that is necessary after state
compromise: neither the fresh KEM public key nor the responding ciphertext can be authenticated
only with a ratchet key that the adversary learned at $t_{\mathrm{comp}}$.  In the statement below,
\emph{UpdateAuth} consists of mutual ML-DSA signatures by the endpoints' long-term identity keys:
the initiator signs
\begin{align*}
  \sigma_{\mathrm{init}} \gets \MLDSA.\Sign\bigl(IK^{DSA}_{sk,A},\;
    &\strlit{UpdateAuth-Init} \,\|\, \mathsf{sid} \,\|\, \mathsf{kem\_id} \\
    &\;\|\, PQ_{pk} \,\|\, \mathsf{epoch} \,\|\, \mathsf{prev}\bigr),
\end{align*}
and the responder signs the canonical bound response:
\begin{align*}
  \sigma_{\mathrm{resp}} \gets \MLDSA.\Sign\bigl(IK^{DSA}_{sk,B},\;
    &\strlit{UpdateAuth-Resp} \,\|\, \mathsf{sid} \,\|\, \mathsf{kem\_id} \\
    &\;\|\, PQ_{pk} \,\|\, ct \,\|\, \mathsf{epoch}' \,\|\, \mathsf{prev}'\bigr),
\end{align*}
where $\mathsf{prev}$ and $\mathsf{prev}'$ are hashes of the respective last accepted ratchet
transcripts.  Authenticating both the KEM public key proposal and the responding ciphertext ensures
that an adversary who possesses Bob's compromised ratchet state cannot answer Alice's $kem\_id$ with
an independently encapsulated ciphertext whose shared secret the adversary knows.  A deployment may
replace these signatures with another authentication mechanism, but it must provide the same
unforgeability guarantee and must not reveal its signing keys in the compromise query.

\paragraph{Oracle semantics.}
For a fixed target session $\pi$ with endpoints $A$ and $B$, the challenger maintains
\[
  (RK,EP,CK_s,CK_r,\mathsf{outstanding},\mathsf{retired},
    \mathcal{K}_{skipped},\mathsf{transcript})
\]
for each endpoint.  The adversary has quantum polynomially many adaptive queries:
\begin{itemize}
  \item $\mathsf{NetSend}(\pi,x)$: deliver, delay, duplicate, reorder, modify, or drop a
        protocol record $x$.  A record is accepted only if its authenticated transcript and
        $\mathsf{kem\_id}$ checks pass.
  \item $\mathsf{Corrupt}(P,t)$: return the complete live state of $P$ at time $t$, including
        current chain/root keys, outstanding KEM secrets, pending ciphertexts, skipped keys,
        and all randomness already sampled.  Erased values are not returned.
  \item $\mathsf{RevealLTK}(P)$: return the ML-DSA signing and other long-term secret keys.
        The target game aborts if the target update's signing key is revealed.
  \item $\mathsf{RevealRNG}(P,t)$: reveal or control the randomness used at time $t$.  The
        target game aborts if this query covers generation of the target KEM keypair.
  \item $\mathsf{RevealKEM}(\mathsf{kem\_id})$: return an outstanding KEM secret key.  The
        target game aborts if the identifier is the target identifier.
  \item $\mathsf{Test}(\pi,e)$: if $(\pi,e)$ is fresh, return either the real first message
        key in target post-update epoch $e$ or an independent uniform 256-bit string;
        otherwise return $\perp$.  Only one Test query is allowed.
\end{itemize}

\paragraph{Freshness and admissible target.}
The target update $(\mathsf{kem\_id}^*,PQ_{pk}^*,ct^*)$ is fresh only if:
\begin{enumerate}
  \item its KEM keypair is generated after $t_{\mathrm{rec}}$ with independent uniform
        randomness and no $\mathsf{RevealRNG}$ query covers that generation;
  \item both update messages are authenticated under identity keys not returned by
        $\mathsf{RevealLTK}$: (a)~$\sigma_{\mathrm{init}}$ on
        $(\strlit{UpdateAuth-Init}, \allowbreak \mathsf{sid}, \allowbreak \mathsf{kem\_id}^*, \allowbreak PQ_{pk}^*, \allowbreak \mathsf{epoch}, \allowbreak \mathsf{prev})$
        verifies under endpoint~$A$'s identity key;
        (b)~$\sigma_{\mathrm{resp}}$ on
        $(\strlit{UpdateAuth-Resp}, \allowbreak \mathsf{sid}, \allowbreak \mathsf{kem\_id}^*, \allowbreak PQ_{pk}^*, \allowbreak ct^*, \allowbreak \mathsf{epoch}', \allowbreak \mathsf{prev}')$
        verifies under endpoint~$B$'s identity key;
        and the signed session, identifier, public key, ciphertext, predecessor hashes, and epochs
        are exactly those accepted by both endpoints;
  \item the matching ciphertext is delivered and decapsulated exactly once, after which the
        KEM secret, old root/chain keys, and any pre-update skipped keys are erased as specified;
  \item no $\mathsf{Corrupt}$ query occurs from target key generation through erasure of the
        tested message key, and no query reveals the target shared secret; and
  \item the tested message key is derived after the completed update and is not in
        $\mathcal{K}_{skipped}$ from before $t_{\mathrm{rec}}$.
\end{enumerate}
Network queries remain unrestricted: the adversary may delay or drop the update, but a target
is not admissible unless the update completes.  Thus availability is not being confused with
confidentiality.

\begin{theorem}[Adaptive single-update PCS bound]
\label{thm:single-update-pcs}
Let $\Pi$ be the ratchet state machine with the acceptance and deletion rules above.  Let
$\mathcal{A}$ be any QPT adversary making at most $Q_{\mathrm{sess}}$ session selections,
$Q_{\mathrm{upd}}$ authenticated update attempts per session, $Q_{\mathrm{KEM}}$ KEM
challenge-relevant encapsulations, and $Q_{\mathrm{KDF}}$ post-update KDF evaluations.
Assume ML-KEM-768 is IND-CCA2 secure against QPT adversaries, ML-DSA-65 is EUF-CMA secure,
and the hidden-input KDF security of Assumption~\ref{asm:kdf-hi} holds.  If $\mathcal{A}$ has
advantage $\epsilon_{\mathrm{PCS}}$ in the adaptive game above, then there exist QPT
reductions $\mathcal{B}_{\mathrm{KEM}}$, $\mathcal{B}_{\mathrm{DSA}}$, and
$\mathcal{B}_{\mathrm{KDF}}$ such that
\[
\begin{aligned}
\epsilon_{\mathrm{PCS}}
 \leq{}&
 Q_{\mathrm{sess}}Q_{\mathrm{upd}}Q_{\mathrm{KEM}}\,
       \Adv^{\mathrm{ind\text{-}cca2}}_{\MLKEM}(\mathcal{B}_{\mathrm{KEM}})
 +2Q_{\mathrm{sess}}Q_{\mathrm{upd}}\,
       \Adv^{\mathrm{euf\text{-}cma}}_{\MLDSA}(\mathcal{B}_{\mathrm{DSA}})\\
&+Q_{\mathrm{KDF}}\,
       \Adv^{\mathrm{hi}}_{\mathrm{KDF}}(\mathcal{B}_{\mathrm{KDF}})
 + \negl(\lambda).
\end{aligned}
\]
Consequently, the tested post-update message key is indistinguishable from uniform, subject
to the freshness conditions.  The bound makes no confidentiality claim for messages sent
before completion, for pre-update skipped keys, or for executions in which the adversary
continues to control either endpoint's RNG or identity-signing key.
\end{theorem}

\begin{proof}[Reduction algorithm]
The KEM reduction guesses a target session, update, and contributing KEM branch, losing at most
$Q_{\mathrm{sess}}Q_{\mathrm{upd}}Q_{\mathrm{KEM}}$.  It embeds the IND-CCA2 challenge public
key as $PQ_{pk}^*$ and uses the challenge ciphertext as $ct^*$.  For all non-target records it
generates honest keys and answers $\mathsf{NetSend}$, corruption, and non-target reveal queries
by running the real algorithms.  For the target update it uses the challenge shared secret
$ss_b$ in both honest endpoint state transitions and never invokes decapsulation on $ct^*$.
Because Bob's response ciphertext is authenticated under $IK^{DSA}_{pk,B}$ via $\sigma_{\mathrm{resp}}$,
an adversary holding Bob's compromised ratchet state cannot substitute an independently encapsulated
ciphertext without forging Bob's signature.  The freshness rules ensure that $\mathcal{A}$ cannot
obtain the target KEM secret or force a forbidden decapsulation query.  If $b=0$, the simulation is
the real game; if $b=1$, the target post-update root and chain keys are pseudorandom after the KDF hybrid.

The DSA reduction answers all signing requests except the guessed target update using its
signing oracles for both endpoints.  A target update accepted with a modified $\mathsf{sid}$,
identifier, public key, response ciphertext, predecessor, or epoch requires forging either
$\sigma_{\mathrm{init}}$ under endpoint $A$'s identity key or $\sigma_{\mathrm{resp}}$ under
endpoint $B$'s identity key, yielding an EUF-CMA forgery against ML-DSA-65 with loss bounded by
$2 Q_{\mathrm{sess}} Q_{\mathrm{upd}}$.
The KDF reduction applies Assumption~\ref{asm:kdf-hi}, \textbf{Case~2 (Ratchet)}: in each
hybrid step it replaces $SS_{PQ}$ with a uniformly random string ($u = SS_{PQ}$, $p = \varepsilon$,
$salt = EP'$, domain label $info$), then invokes the partial-uniformity game to show the
post-update entropy-pool, root-key, chain-key, and message-key derivations are
computationally indistinguishable from independent uniform strings.  There are at most
$Q_{\mathrm{KDF}}$ such replacements; the triangle inequality gives the displayed sum.
Duplicate, reordered, and timed-out records cannot add a term: the retired-set and deterministic
predecessor rule make them either reject or repeat an already accepted transition without changing
state.  Dropped records simply prevent the freshness predicate from holding.
\end{proof}

\subsection{Authentication: Bundle Identity Binding}
\label{sec:fsremark}

\begin{securityclaim}[Identity Binding]
\label{thm:auth}
Under Assumption~\ref{asm:mldsa}, if there exists a QPT adversary
$\calA_{\mathrm{quant}}$ that forges a valid Pre-Key Bundle with advantage $\epsilon$, then
there exists a
reduction $\calB$ that breaks the EUF-CMA security of ML-DSA-65 with advantage
$\epsilon' \geq \epsilon - \negl(\lambda)$.
\end{securityclaim}

\begin{proof}[Proof Sketch]
Let $\calB$ be a reduction interacting with an EUF-CMA challenger $\mathcal{C}$ for ML-DSA-65.
$\calB$ receives a challenge verification key $vk^*$ and embeds it as Bob's identity key $IK^{DSA}_{pk,B}$ in the
simulated P2P network.  Signing queries from $\calA_{\mathrm{quant}}$ are forwarded to
$\mathcal{C}$'s signing oracle.

Suppose $\calA_{\mathrm{quant}}$ substitutes a pre-key bundle while Bob accepts it as
authentic.  It must publish a malicious bundle $\mathsf{Bundle}'_B$ signed under Bob's
identity key $IK^{DSA}_{pk,B}$ that substitutes Bob's pre-keys ($SPK_B$, $PQ\_SPK_B$, or
one-time keys) with keys chosen by the adversary.

The bundle signature covers the full $\mathsf{BundlePayload}$ including the hashes of the
OTPK and PQ-OTPK batches (Section~\ref{sec:bundle}).  If the adversary publishes a modified
bundle with any substituted pre-key, the corresponding batch hash or public key changes.
Since Bob is honest, this signature must be forged.  $\calB$ extracts the message and the
signature forgery, submitting it to the EUF-CMA challenger $\mathcal{C}$ to win.

The argument therefore establishes bundle authenticity only.  Any stronger claim about
active MITM resistance must separately specify the authentication transcript and cannot
reduce a quantum-active adversary's inability to compute an X25519 shared secret to CDH,
because X25519 is not quantum-resistant.
\end{proof}

\subsection{Post-Quantum Forward Secrecy}

\begin{securityclaim}[PQ-FS proof sketch]
\label{thm:pqfs}
Under Assumptions~\ref{asm:mlwe}, \ref{asm:kdf-hi}, and the stated freshness and deletion
conditions, if there exists a QPT adversary
$\calA_{\mathrm{quant}}$ winning $\PGame^{\mathrm{PQ\text{-}FS}}_{\calA}(\lambda)$
(Definition~\ref{def:pqfs}) with advantage $\epsilon$, then the following proof sketch gives a QPT reduction
$\calB$ that breaks IND-CCA2 security of ML-KEM-768 with advantage
$\epsilon' \geq (\epsilon - \negl(\lambda))/Q_{\mathrm{KEM}}$, where
$Q_{\mathrm{KEM}}$ is the number of challenged encapsulations in the multi-instance reduction.
\end{securityclaim}

\begin{proof}[Proof Sketch]
The final bound is $\epsilon' \geq (\epsilon - \negl(\lambda))/Q_{\mathrm{KEM}}$,
where the $1/Q_{\mathrm{KEM}}$ factor comes from the multi-instance KEM selection loss
explained in the ``Bounding $\epsilon'$'' paragraph below.

\medskip\noindent
\textbf{Game $\Hgame{0}$:} The real PQ-FS game $\PGame^{\mathrm{PQ\text{-}FS}}_{\calA}(\lambda)$.
$\calA_{\mathrm{quant}}$'s advantage in $\Hgame{0}$ is $\epsilon$ by hypothesis.

\medskip\noindent
\textbf{Game $\Hgame{1}$:} Identical to $\Hgame{0}$, except that the challenger, upon choosing
Bob's bundle for the target session $\pi^s_i$, embeds the IND-CCA2 challenge public key $pk^*$
as $PQ\_OTPK_{pk,B}$.  The corresponding ciphertext $ct^*$ (from the IND-CCA2 challenger)
replaces $ct_2$ in Alice's handshake message $M_0$.

\textit{Transition $\Hgame{0} \to \Hgame{1}$:} From $\calA_{\mathrm{quant}}$'s view, this
substitution is syntactically identical to the real protocol: $pk^*$ is a valid ML-KEM public
key, and $ct^*$ is a valid encapsulation thereof.  No oracle is modified.  The two games are
therefore \emph{perfectly indistinguishable}:
$|\Pr[\calA\text{ wins }\Hgame{1}] - \Pr[\calA\text{ wins }\Hgame{0}]| = 0$.

\medskip\noindent
\textbf{Game $\Hgame{2}$:} Identical to $\Hgame{1}$, except that $SS_{PQ2}$ is replaced by a
uniformly random string $u \getsr \bits^{32}$, independently of $ct^*$.  This corresponds to
the IND-CCA2 challenger providing the ``random'' branch ($ss_1$) rather than the real shared
secret.

\textit{Transition $\Hgame{1} \to \Hgame{2}$:}  In $\Hgame{1}$, $SS_{PQ2}$ is the real
decapsulation of $ct^*$ under $pk^*$.  In $\Hgame{2}$, $SS_{PQ2}$ is random.  Suppose
$\calA_{\mathrm{quant}}$ distinguishes $\Hgame{1}$ from $\Hgame{2}$ with advantage $\delta$.
Then the reduction $\calB$, who receives $(pk^*, ct^*, ss_b)$ from the IND-CCA2 challenger,
runs $\calA_{\mathrm{quant}}$ in the $\Hgame{1}$ simulation but uses $ss_b$ in place of
$SS_{PQ2}$.  $\calB$ outputs $b' = 0$ if $\calA_{\mathrm{quant}}$ wins, and $b' = 1$ otherwise.
The IND-CCA2 decapsulation oracle handles all $\calA_{\mathrm{quant}}$'s decapsulation queries
on $ct \neq ct^*$; the query $ct = ct^*$ is not permitted by the IND-CCA2 rules (and
$\calA_{\mathrm{quant}}$'s PQ-FS freshness constraint prevents Reveal queries that would expose
$PQ\_OTPK_{sk}$ after decapsulation).  Thus $\Adv^{\mathrm{ind\text{-}cca2}}_{\MLKEM}(\calB)
\geq \delta / Q_{\mathrm{KEM}}$, accounting for guessing the target pre-key instance.

\medskip\noindent
\textbf{Game $\Hgame{3}$:}  In $\Hgame{2}$,
$SS_{\text{hybrid}} = \hexlit{0xFF} \| SS_{cl} \| SS_{PQ1} \| u$.
\textbf{Scope note:} this argument covers the case where the PQ-OTPK branch is present
(i.e.\ $SS_{PQ2}$ corresponds to the OTPK encapsulation $ct_2$).  Note that $SS_{PQ1}$
(from the semi-static $PQ\_SPK$ encapsulation) remains the real shared secret; only $SS_{PQ2}$
has been replaced by $u$.  In the \emph{SPK-only fallback} (Remark~\ref{rem:spkonly}, when no
OTPK is available), the argument instead embeds the challenge in $SS_{PQ1}$; in that case the
security guarantee degrades to session-level PQ-FS (granularity of $PQ\_SPK$ rotation), as
noted there.

This transition applies Assumption~\ref{asm:kdf-hi}, \textbf{Case~1 (Handshake, Branch~1a)}, with the
following identification of components:
\begin{itemize}
  \item $p = \hexlit{0xFF} \,\|\, SS_{cl} \,\|\, SS_{PQ1}$ (known or partially known to
        $\calA_{\mathrm{quant}}$ if DH keys are later revealed).
  \item $u = SS_{PQ2}$ (computationally uniform by Game~$\Hgame{2}$).
  \item $salt = \mathbf{0}^{32}$ (public).
  \item $info = AD \,\|\, \flen{EK_{pk,A}} \,\|\, EK_{pk,A} \,\|\, \flen{ct_1} \,\|\, ct_1
               \,\|\, \flen{ct_2} \,\|\, ct_2$ (public transcript binder, satisfying the
        ciphertext-binding precondition of Remark~\ref{rem:combiner}).
\end{itemize}
Even though $p$ and $salt$ are public, the one-uniform-component argument guarantees that
$\mathsf{HMAC}_{\mathbf{0}^{32}}(p \,\|\, u)$ is pseudo-random because $u$ acts as a hidden
key for HMAC (dual-PRF property~\cite{krawczyk2010hkdf}).  Concretely, the output is
\begin{align*}
  OKM &= \HKDF\bigl(ikm = SS_{\text{hybrid}},\; salt = \mathbf{0}^{32},\; info,\; \ell = 64\bigr), \\
  \text{where}\quad info &= AD \,\|\, \flen{EK_{pk,A}} \,\|\, EK_{pk,A} \,\|\, \flen{ct_1} \,\|\, ct_1 \,\|\, \flen{ct_2} \,\|\, ct_2.
\end{align*}
By Assumption~\ref{asm:kdf-hi} (Case~1, Branch~1a), $OKM$ is pseudorandom, hence $MK_e$ is pseudorandom.
$\calA_{\mathrm{quant}}$'s advantage in $\Hgame{3}$ is therefore $\negl(\lambda)$.

\textit{Transition $\Hgame{2} \to \Hgame{3}$:}  The distinguishing advantage between
$\Hgame{2}$ and $\Hgame{3}$ is at most $\Adv^{\mathrm{hi}}_{\mathrm{KDF}}(\mathcal{B}_{\mathrm{KDF}}) \in \negl(\lambda)$
by Assumption~\ref{asm:kdf-hi} (Case~1, Branch~1a).

\medskip\noindent
\textbf{Bounding $\epsilon'$:}  The reduction $\calB$ receives a single IND-CCA2 challenge $(pk^*, ct^*)$ and embeds $pk^*$ into the fresh pre-key of the target handshake ($PQ\_OTPK_{pk,B}$, or $PQ\_SPK$ in fallback).  Among the $Q_{\mathrm{KEM}}$ candidate pre-keys generated across the experiment, $\calB$ correctly guesses the target instance with probability at least $1/Q_{\mathrm{KEM}}$.

Combining the hybrid transitions:
\[
  \epsilon = |\Pr[\calA\text{ wins }\Hgame{0}] - \Pr[\calA\text{ wins }\Hgame{3}]|
           \leq \delta + \Adv^{\mathrm{hi}}_{\mathrm{KDF}}(\mathcal{B}_{\mathrm{KDF}}) + \negl(\lambda),
\]
which implies $\delta \geq \epsilon - \Adv^{\mathrm{hi}}_{\mathrm{KDF}}(\mathcal{B}_{\mathrm{KDF}}) - \negl(\lambda)$.  Accounting for the pre-key guessing factor $1/Q_{\mathrm{KEM}}$, the reduction achieves:
\[
  \epsilon' \geq \frac{\epsilon - \Adv^{\mathrm{hi}}_{\mathrm{KDF}}(\mathcal{B}_{\mathrm{KDF}}) - \negl(\lambda)}{Q_{\mathrm{KEM}}}.
\]
\end{proof}

\begin{remark}[Role of the Classical Component and KEM-Combiner Applicability]
\label{rem:combiner}
The concatenation-combiner theorem of Giacon et al.\ \cite{giacon2018kem} is proven for two
KEMs.  Star-Mesh combines X25519 (a Diffie--Hellman function, not natively a KEM) with
ML-KEM-768.  We apply the theorem with the following protocol-specific adaptation: the X25519
ephemeral key $EK_{pk,A}$ is treated as the KEM's public key, the DH output $SS_{cl}$ as its
implicit ``shared secret'', and the ephemeral key itself is bound into the HKDF $info$ string
in place of an explicit ciphertext.  Security of the classical component then additionally
relies on the CDH assumption over Curve25519.  Binding $EK_{pk,A}$, $ct_1$, and $ct_2$ into
$info$ satisfies the ciphertext-binding precondition of \cite{giacon2018kem}, guarding against
related-ciphertext and re-encapsulation attacks.  This is a protocol-specific adaptation, not a
direct application of the theorem; the CDH assumption is required in addition to HKDF-PRF.

If X25519 remains computationally secure (no CRQC), $SS_{cl}$ alone makes $SS_{\text{hybrid}}$
pseudorandom under the stated assumptions, providing classical forward secrecy.  The ML-KEM
component provides additional PQ-FS against a CRQC.  The two components are
\emph{complementary}: security holds if either is secure under the modeled assumptions.
\end{remark}

\subsection{Post-Compromise Security}
\label{sec:pcsproof}

\begin{remark}[PCS healing — relationship to Theorem~\ref{thm:single-update-pcs}]
\label{rem:pcs}
Security Claim~\ref{thm:pqfs} establishes PQ-FS for the initial handshake.
Post-Compromise Security after an authenticated ratchet update is covered by
Theorem~\ref{thm:single-update-pcs}, whose bound is:
\[
\begin{aligned}
\epsilon_{\mathrm{PCS}}
 \leq{}&
 Q_{\mathrm{sess}}Q_{\mathrm{upd}}Q_{\mathrm{KEM}}\,
       \Adv^{\mathrm{ind\text{-}cca2}}_{\MLKEM}(\mathcal{B}_{\mathrm{KEM}})
 +2Q_{\mathrm{sess}}Q_{\mathrm{upd}}\,
       \Adv^{\mathrm{euf\text{-}cma}}_{\MLDSA}(\mathcal{B}_{\mathrm{DSA}})\\
&+Q_{\mathrm{KDF}}\,
       \Adv^{\mathrm{hi}}_{\mathrm{KDF}}(\mathcal{B}_{\mathrm{KDF}})
 + \negl(\lambda).
\end{aligned}
\]
The reduction in Theorem~\ref{thm:single-update-pcs} guesses the target session, update, and
KEM branch, paying the joint factor $Q_{\mathrm{sess}}Q_{\mathrm{upd}}Q_{\mathrm{KEM}}$, and
separately handles mutual update authenticity ($\sigma_{\mathrm{init}}$ and $\sigma_{\mathrm{resp}}$)
via an EUF-CMA reduction losing $2Q_{\mathrm{sess}}Q_{\mathrm{upd}}$.  The KDF hybrid pays
$Q_{\mathrm{KDF}}$ by the triangle inequality over the pure hidden-input KDF game.
Corollary~\ref{cor:pcs} records the qualitative healing statement;
quantitative PCS security is entirely captured by Theorem~\ref{thm:single-update-pcs}.
\end{remark}

\begin{corollary}[PCS Healing]
\label{cor:pcs}
Under the conditions of Theorem~\ref{thm:single-update-pcs}, confidentiality of all epochs $e'$
satisfying conditions \emph{(a)}, \emph{(b)}, and \emph{(c)} of Definition~\ref{def:pcs} is
restored after one complete PQ ratchet round-trip, under the IND-CCA2 security of ML-KEM-768.

In particular, note the following limitations.  First, out-of-order delivery: if the
PQ-responder's ciphertext reply for a $kem\_id$ is delayed, the round-trip may not complete within a
bounded window; healing is delayed accordingly.  Second, dropped PQ-step messages: if
$kem\_id$ or its matching ciphertext is permanently lost (e.g., via DHT mailbox TTL expiry
or eviction rather than mere delay), the round-trip cannot complete.  In this case the
PQ-initiator must retire the entry and re-initiate a fresh PQ step with a new keypair;
retry policy and timeout values are implementation concerns left to a full protocol specification.
Third, skipped-key cache: message keys cached in $\mathcal{K}_{skipped}$ from epochs before
$t_{rec}$ are not covered by this corollary (those message keys are already exposed by the
prior compromise).  Fourth, PQ ratchet counter: if $\mathsf{pq\_step\_counter} > 0$ at
$t_{comp}$, the PQ-initiator may not send a fresh $PQ^{loc}_{pk}$ until the counter expires
(at most $\Delta$ additional messages), delaying the start of the round-trip.
Fifth, and critically, \emph{identity key survival and signing-oracle isolation}: recovery
proceeds in two cases.
\begin{itemize}
  \item \textbf{Passive-after-compromise adversary}: an adversary that reads session state at
    $t_{comp}$ but thereafter makes no further queries (no signing-oracle access, no active
    injections).  In this case, healing depends only on KEM IND-CCA2 and a clean RNG at
    $t_{rec}$; $IK^{DSA}_{sk}$ need not remain in hardware-isolated storage for
    post-compromise security to hold against this weaker adversary.
  \item \textbf{Active adversary}: one that continues to inject, modify, or replay messages
    after $t_{comp}$, or that queries the enclave signing oracle during the compromise window.
    Against this stronger model, this corollary requires the full
    Assumption~\ref{asm:idkey-isolation}: $IK^{DSA}_{sk}$ is not exfiltrated \emph{and} the
    adversary has no signing-oracle access during the compromise window.  If either condition
    fails, the adversary can forge or replay $\sigma_{\mathrm{init}}$ and
    $\sigma_{\mathrm{resp}}$ indefinitely, and healing cannot be guaranteed against this
    adversary class.
\end{itemize}
PCS holds unconditionally against a passive-after-compromise adversary, and under
Assumption~\ref{asm:idkey-isolation} against an active adversary.
\end{corollary}

\section{Metadata Resistance}
\label{sec:metadata}
% ============================================================

Star-Mesh achieves metadata resistance through two complementary mechanisms.

\paragraph{DHT Mailbox Indirection.}
Each node maintains a \emph{mailbox} in the Kademlia DHT keyed by a pseudonymous address
$\mathsf{addr}_i = H(IK^{DSA}_{pk,i} \| \mathsf{epoch})$, rotated periodically.  Senders
deposit encrypted messages at the mailbox address; recipients perform constant-rate polling.
This severs the direct IP-to-recipient link exploitable by a passive observer of DHT traffic.

\paragraph{Onion-Routing Overlay.}
Message delivery and mailbox retrieval are routed through a libp2p-based onion-routing overlay
following the Loopix \cite{loopix} architecture.  Each message is layered with Sphinx-format
encryption \cite{sphinx} over a randomly sampled sequence of mix nodes.  Dummy cover traffic is
generated at a constant rate $\lambda_{cover}$ to prevent traffic analysis via timing or volume.

\begin{remark}[Sender-Receiver Unlinkability — Heuristic Modeling]
\label{rem:unlinkability}
Under Assumption~\ref{asm:mixnet} (at most $f < 1/2$ of mix nodes are adversarially controlled)
and assuming constant-rate cover traffic, the probability that $\calA_{\mathrm{quant}}$ links a
sending event to a receiving event is modeled heuristically as at most $\frac{f}{1-f} \cdot \frac{1}{n_{\mathrm{mix}}} +
\negl(\lambda)$, where $n_{\mathrm{mix}}$ is the number of honest mix nodes on the path.
This expression is a conceptual approximation derived from the corruption-fraction threat framework
rather than a formal cryptographic bound; see the note below.
\end{remark}

\noindent The formulation above is an \emph{informal modeling heuristic}, adapted from the
corruption-fraction threat framework underlying Loopix \cite{loopix}.  We do not claim that
Section~4.3 of \cite{loopix} states this closed-form expression; that work evaluates
empirical end-to-end anonymity under Poisson mixing and constant-rate cover traffic.
Our use of $\frac{f}{1-f} \cdot \frac{1}{n_{\mathrm{mix}}}$ serves strictly to parameterise
system-level risk in Star-Mesh under Assumption~\ref{asm:mixnet}.  We make no new claims about
mixnet anonymity beyond this heuristic model.  Star-Mesh's primary contribution is the integration
of this routing overlay with the hybrid post-quantum ratchet layer.

\paragraph{Empirical Queue Simulation Results.}
To evaluate the packetization discipline under the signed ratchet design required by Theorem~\ref{thm:single-update-pcs}, the
repository provides a reproducible discrete-time queue simulation in \texttt{poc/python/mixnet\_sim.py}.
The experiment simulates 30 mix nodes over three mix hops, with node service capacity $C = 2$
packets/slot, symmetric cover traffic ($\lambda_{\mathrm{cover}} = \lambda$), and an adversarial compromise
fraction of $20\%$ ($f = 0.2$).  Because state compromise cannot be detected locally, \emph{every}
periodic KEM ratchet update (triggered every $\Delta = 50$ messages) carries mutual ML-DSA-65 identity
signatures (\emph{UpdateAuth}, $3{,}309$~bytes each) alongside ML-KEM-768 keys ($1{,}184$~B) or ciphertexts ($1{,}088$~B).
Bundled with standard 192-byte application payloads, these signed update messages total $4{,}685$~B (initiator)
and $4{,}589$~B (responder).  To preserve the constant-packet-size discipline of the Sphinx mixnet ($1{,}500$-byte MTU
with 96-byte onion routing headers), the transport layer fragments each signed update into a bounded train of
4 Sphinx packets ($\lceil 4{,}685 / 1{,}404 \rceil = 4$), while intermediate conversational messages
($98\%$ of transmissions) traverse the network as single 1{,}500-byte Sphinx packets without fragmentation.
In the simulation, an authenticated update is counted as delivered if and only if all 4 fragments successfully
traverse the mixnet to the destination.

We formally define the \emph{Entry--Exit Linkability} metric as the empirical fraction of delivered messages
for which an adversary concurrently controls both the ingress mix node (first hop) and egress mix node (last hop)
along the packet's onion-routed path:
\[
  \mathrm{Linkability} \coloneqq \frac{1}{|\mathcal{M}_{\mathrm{del}}|} \sum_{m \in \mathcal{M}_{\mathrm{del}}} \mathbb{I}\bigl(\mathrm{entry}(m) \in \mathcal{C} \;\land\; \mathrm{exit}(m) \in \mathcal{C}\bigr),
\]
where $\mathcal{C}$ denotes the set of compromised mix nodes ($|\mathcal{C}| / n_{\mathrm{total}} = f$) and
$\mathcal{M}_{\mathrm{del}}$ is the set of completely delivered messages.  This metric serves as an empirical lower-bound
proxy for path-correlation vulnerability under fractional node compromise.

The simulation findings validate the architectural hypothesis:
\begin{enumerate}
  \item \textbf{Transport MTU Compliance and the Burst-Fingerprint Limitation:} Across all simulated packets in the 13 simulation runs of Table~\ref{tab:mixnet_sim}, the Sphinx
        packet MTU violation rate was strictly \textbf{0\%}.  While raw signed updates ($> 4.5$~KB) cannot fit
        within a single Ethernet MTU, fragmenting them into 4 standard 1{,}500-byte Sphinx packets satisfies the
        network MTU constraint.  However, this multi-packet fragmentation introduces an operational limitation:
        the periodic transmission of a 4-packet burst every $\Delta = 50$ messages creates an identifiable traffic volume burst fingerprint.
        This burst pattern contradicts theoretical claims of metadata security without leakage: a passive network adversary observing flow volume or packet inter-arrival times across mix nodes can correlate these periodic 4-packet bursts to identify communicating pairs, even though individual packets are encrypted and padded to uniform size.
        Routine conversational messages traverse the network as single packets ($98\%$ of transmissions), accentuating the contrast with ratchet update bursts.

        \paragraph{Mitigating Burst Fingerprints.}
        To eliminate this traffic-analysis vector in production deployments, several countermeasures may be deployed:
        (i)~\emph{dummy burst injection}, wherein nodes periodically inject dummy 4-packet trains at randomized (e.g., Poisson-distributed) intervals independent of ratchet updates;
        (ii)~\emph{uniform train padding}, wherein routine conversational messages are padded with dummy Sphinx packets to constant multi-packet trains ($k=4$); or
        (iii)~\emph{dribble fragmentation}, wherein KEM public keys, ciphertexts, and signatures are streamed incrementally across consecutive single-packet conversational messages (similar to the chunked streaming in SPQR \cite{signal_spqr}), trading a wider post-compromise exposure window for a smooth, single-packet traffic profile.
  \item \textbf{Impact of Multi-Packet Fragment Trains on Queueing and Churn:} Under zero churn, delivery
        remains near-lossless ($\ge 99.9\%$) for loads up to $\lambda = 5.0$.  The 4-packet fragment trains
        injected during KEM updates slightly increase queue pressure at the saturation threshold ($\lambda = 10.0$,
        where p95 delay reaches 279 slots).  Under churn ($10\%$--$30\%$), the delivery rate for signed updates
        is bounded by the probability that all 4 fragments survive intermediate node dropouts, reinforcing the need
        for transport-layer retransmissions and acknowledgments.
        This collapse is an analytical artifact of queueing capacity saturation in the discrete-event model
        rather than a protocol or cryptographic bottleneck: because cover traffic is generated at
        $\lambda_{\mathrm{cover}} = \lambda$, total network ingress is $2\lambda$ packets/slot.
        Traversing 3 hops requires $3 \times 2\lambda = 6\lambda$ per-hop forwarding operations per slot.
        With 30 nodes each serving $C = 2$ packets/slot, aggregate network capacity is strictly 60 packet-operations/slot.
        At $\lambda = 10$, utilization reaches $100\%$ ($\rho = 1.0$); at $\lambda = 20$, offered demand is 120
        packet-operations/slot ($200\%$ overload), causing queues to grow monotonically throughout the 5{,}000-slot run
        and unserved packets remaining in queues at run termination to be counted as undelivered.
        Furthermore, the simulation operates in abstract discrete slots without an explicit physical time mapping;
        in operational mixnet deployments, mix nodes process thousands of packets per second, and per-hop Poisson
        delays are calibrated to physical milliseconds.
        Under churn ($10\%$--$30\%$), delivery rate degrades proportionally to route interruption,
        highlighting that transport-layer reliability requires end-to-end ACKs and retransmissions.
  \item \textbf{Scope Limitation:} We emphasize that this queue model simulates steady-state ratchet
        exchanges; one-time handshake messages ($M_0 = 4{,}256$~B) and signed pre-key bundles
        require multi-packet Sphinx trains (4 fragments for $M_0$ as $\lceil 4{,}256 / 1{,}404 \rceil = 4$) or direct mailbox deposition.
\end{enumerate}

\paragraph{Amortised Cryptographic Cost.}
The cryptographic overhead of the post-quantum ratchet is governed by the requirement of post-compromise security (Theorem~\ref{thm:single-update-pcs}):
\begin{enumerate}
  \item \textbf{Primary Specification: Signed Ratchet for PCS (Theorem~\ref{thm:single-update-pcs}):} Because state compromise is silent and undetectable, an endpoint cannot determine when its ratchet state has been exfiltrated.  To guarantee healing against an adversary in possession of the compromised symmetric ratchet state, \emph{every} periodic KEM update must authenticate both the initiator's public key proposal and the responder's ciphertext response under their long-term identity keys via ML-DSA-65 signatures (\emph{UpdateAuth}, $3{,}309$~bytes each).  This requires $1{,}184 + 3{,}309 = 4{,}493$~bytes for the initiator step and $1{,}088 + 3{,}309 = 4{,}397$~bytes for the responder reply, totaling $8{,}890$~bytes per update round-trip.  Amortised across both conversation directions over ratchet interval $\Delta = 50$ (100 messages total in the alternating single-initiator baseline), the per-message cryptographic overhead is:
        \[
          \frac{(|PQ\_pk| + |\sigma_{\MLDSA}|) + (|PQ\_ct| + |\sigma_{\MLDSA}|)}{2\Delta}
          = \frac{8{,}890}{100}
          = 88.90 \;\text{bytes/message.}
        \]
        Because each signed update payload exceeds the 1{,}500-byte MTU, each update is fragmented by the transport layer into a bounded train of 4 Sphinx packets.
        In the worst-case scenario where both communicating endpoints trigger concurrent updates at the expiration of their independent counters (Remark~\ref{rem:concurrent}), each party conducts an independent signed update round-trip, injecting $2 \times 8{,}890 = 17{,}780$~bytes over the 100 conversational messages, yielding an upper bound of $177.80$~bytes/message.
  \item \textbf{Theoretical Lower Bound (Unsigned Baseline):} If an adversary were assumed never to compromise the internal symmetric state (or if compromise were signaled out-of-band), updates could theoretically omit signatures and rely solely on symmetric chain keys.  In that unauthenticated baseline, the raw ML-KEM-768 material would add $1{,}184 + 1{,}088 = 2{,}272$~bytes per round-trip, or $22.72$~B/msg ($45.44$~B/msg in concurrent dual-initiation).  However, as proven in Section~\ref{sec:single-update-theorem}, this unsigned baseline \emph{fails to provide post-compromise security} under state compromise.  Star-Mesh therefore specifies the signed design (88.90~B/msg baseline, 177.80~B/msg worst case) as its standard protocol.
\end{enumerate}

\paragraph{Decoupled Overlay and DHT Transport Overhead.}
We emphasize an important architectural separation: the cryptographic ratchet wire overhead above is
strictly decoupled from the transport and routing overhead of the underlying decentralized network.
A peer-to-peer messaging system over a Kademlia DHT incurs operational traffic for key lookup,
record maintenance, and mailbox polling; however, this traffic is a property of the P2P routing
overlay and is identical whether sessions use classical or post-quantum ratcheting.

Specifically, at the data layer, a mailbox routing record introduces a minimal static addressing
footprint (a 20-byte node ID plus an 8-byte TTL field, and a 32-byte polling request header).
However, network-layer transport costs cannot be represented as a static per-message addend:
\begin{enumerate}
  \item \textbf{Iterative DHT Lookups:} Resolving a recipient's pre-key bundle or mailbox address
        requires iterative Kademlia queries ($\alpha = 3$ concurrent paths over $O(\log N)$ hops),
        where each response exchanges lists of up to $k = 20$ contact tuples ($26$--$38$ bytes each).
        While lookups are amortised across ongoing sessions via routing-table and contact caching,
        initial discovery or route repairs under churn generate kilobyte-scale signaling overhead.
  \item \textbf{Replication and Churn:} Maintaining mailbox availability requires periodic republishing
        to the $k$ closest nodes; in networks with high churn, maintenance bandwidth scales with churn rate.
  \item \textbf{Continuous Polling vs.\ Message Arrival Rate:} Metadata-resistant constant-rate polling
        consumes network bandwidth as a function of time (bytes per second), not per application message.
        Under low message arrival rates, polling traffic amortised per delivered message is naturally
        substantially higher than under continuous dialogue.
  \item \textbf{Mixnet Packet Padding and Fragmentation:} As detailed in Section~\ref{sec:metadata}, messages and
        polling queries traversing the mixnet overlay are encapsulated in constant-size Sphinx packets
        padded to a 1{,}500-byte MTU.  Within this packet discipline, the 88.90-byte amortised PQ ratchet
        overhead is absorbed across periodic 4-packet Sphinx fragment trains every $\Delta$ messages, preserving
        the constant-packet-size discipline across the network.
\end{enumerate}
Consequently, a complete empirical accounting of network-level bandwidth under realistic churn and
polling models requires high-fidelity network emulation (planned in our engineering roadmap),
whereas the $88.90$ bytes/message reported here represents the invariant cryptographic overhead
mandated to achieve post-compromise security under state compromise.

\paragraph{Computational Cost.}
ML-KEM-768 encapsulation and decapsulation execute in well under 1\,ms on modern hardware
\cite{nist_fips203}, triggered at most once every 50 messages.
To validate the computational practicality of our protocol, we micro-benchmarked our Rust
prototype over 1{,}000 iterations on an Apple M1 Air (8-core CPU, macOS 26.5.2, \texttt{rustc} 1.97.1),
compiled in Rust \texttt{release} mode (\texttt{opt-level = 3}, link-time optimisation enabled,
\texttt{cargo build {-}{-}release}).
The micro-benchmark is executed in release mode and can be reproduced with \texttt{make rust-poc}
(or directly via \texttt{cargo run {-}{-}release {-}{-}manifest-path poc/rust/Cargo.toml}).
The benchmark is implemented as a hand-rolled 1{,}000-iteration
timing loop using \texttt{std::time::Instant} (\texttt{poc/rust/src/main.rs}, Phase~5),
reporting mean, standard deviation, and percentiles computed from the sorted sample.
This methodology is representative but not equivalent to a statistically rigorous harness
such as \texttt{criterion}: there is no warm-up phase, no outlier detection, and statistics
are computed over a single run.  The figures should therefore be read as indicative
performance magnitudes rather than confidence-bounded latency guarantees.  Under this
platform:
\begin{itemize}
  \item \textbf{PQ-X3DH Handshake} (initiator + responder): mean execution time of $793.71\,\mu\text{s}$
        (std dev: $36.71\,\mu\text{s}$; p50: $787.17\,\mu\text{s}$; p95: $803.13\,\mu\text{s}$; p99: $1{,}032.75\,\mu\text{s}$).
  \item \textbf{PQ Ratchet Round-trip} (init + encaps + decaps with mutual ML-DSA-65 signing and verification): mean execution time of $1{,}530.92\,\mu\text{s}$ ($\approx 1.53\,\text{ms}$;
        std dev: $669.22\,\mu\text{s}$; p50: $1{,}381.96\,\mu\text{s}$; p95: $2{,}847.63\,\mu\text{s}$; p99: $3{,}712.83\,\mu\text{s}$).
\end{itemize}
These low-latency execution times confirm the computational practicality of the scheme for consumer endpoints.
The handshake latency includes four ML-KEM-768 operations (two encapsulations by Alice and two decapsulations by Bob for $ct_1$ and $ct_2$ in the full handshake with OTPK),
four X25519 scalar multiplications, and KDF/hash logic. The ratchet round-trip includes
one ML-KEM-768 key generation, encapsulation, and decapsulation, HKDF root mixing, and mutual
ML-DSA-65 signature generation and verification ($\sigma_{\mathrm{init}}$ and $\sigma_{\mathrm{resp}}$)
mandated by Theorem~\ref{thm:single-update-pcs}.
Even with full mutual asymmetric signing on every periodic update, the entire round-trip completes in approximately $1.5$\,ms, which is imperceptible to users; for reference ML-KEM-768 reference implementation performance figures, see the NIST FIPS~203 supporting documentation \cite{nist_fips203}.
The dominant computational overhead in Star-Mesh is expected to be the mixnet onion routing (Sphinx packet construction \cite{sphinx}), which requires multiple asymmetric operations per hop and is independent of the PQC primitives.

\section{Assumptions and Limitations}
\label{sec:assumptionslimitations}
% ============================================================

We consolidate the protocol's assumptions and known limitations here for clarity.

\begin{enumerate}
  \item \textbf{ML-DSA-65 EUF-CMA security} (Assumption~\ref{asm:mldsa}): ML-DSA-65 is secure
        against existential forgery under chosen-message attacks.
  \item \textbf{CDH hardness on Curve25519} (Assumption~\ref{asm:cdh}): CDH on Curve25519 is hard
        against classical adversaries, required for implicit authentication ($DH_1$).
  \item \textbf{Module-LWE hardness} (Assumption~\ref{asm:mlwe}): ML-KEM-768 is IND-CCA2
        secure under MLWE with $n = 256$, $k = 3$.
  \item \textbf{HKDF as Dual-PRF and Extractor} (Assumption~\ref{asm:hkdf}): HKDF-SHA3-256 is modeled as a
        two-stage extract-then-expand PRF and computational extractor following \cite{krawczyk2010hkdf}.
  \item \textbf{Dual-PRF / One-Uniform-Component KDF Security} (Assumption~\ref{asm:kdf-hi}): Whenever
        concatenated IKM contains at least one uniform component, HKDF extraction yields pseudorandom
        output under both public salt (handshake) and secret salt (ratchet), isolating KDF analysis from
        KEM/DH reductions.
  \item \textbf{BLAKE3-KDF as PRF} (Assumption~\ref{asm:blake3}): BLAKE3's keyed hashing
        mode is modeled as a PRF; required for pseudorandomness of per-message keys $MK_i$
        and hence for message confidentiality.
  \item \textbf{Deletion schedule enforced} (Assumption~\ref{asm:deletion}): An operational
        assumption; not proven by the protocol logic but required for FS and PCS.
  \item \textbf{RNG integrity after $t_{rec}$} (Assumption~\ref{asm:rng}): The RNG is clean
        from $t_{rec}$ onward.  A compromised RNG during PQ ratchet key generation makes PCS
        unachievable for that update.
  \item \textbf{Identity key isolation across state compromise} (Assumption~\ref{asm:idkey-isolation}):
        \emph{PCS holds only if the identity signing key ($IK^{DSA}_{sk}$) remains uncompromised during
        and after ephemeral state compromise.}  On a single, unprotected device this key and the session
        state occupy the same memory; total device expropriation would leak both, making recovery
        impossible.  This assumption requires the identity key to reside in a hardware-isolated environment
        (HSM, secure enclave, or OS-protected keystore) that is not returned by the Corrupt oracle.
        The ratchet's PCS addresses a distinct threat from what the identity key alone provides:
        static identity keys supply authentication, whereas the ratchet continuously refreshes quantum-resistant
        symmetric confidentiality, using the hardware-isolated signing key strictly to prevent active
        ciphertext substitution during healing.  A reviewer asking ``why does the ratchet add anything beyond
        the identity key?'' should read Section~\ref{sec:secmodel}: the EUF-CMA term in Theorem~\ref{thm:single-update-pcs}
        is a guard against active substitution, not the primary confidentiality mechanism; ML-KEM IND-CCA2
        provides the confidentiality recovery.
  \item \textbf{Mixnet honesty fraction} (Assumption~\ref{asm:mixnet}): At most $f < 1/2$ of
        mix nodes are adversarially controlled.
  \item \textbf{DHT Sybil resistance} (Assumption~\ref{asm:dht}): The DHT is operationally
        protected against Sybil and eclipse attacks; this is not proven by the protocol.
  \item \textbf{Out-of-order delivery and PCS} (Corollary~\ref{cor:pcs}): PCS restoration is
        conditional on the round-trip completing; delayed network delivery defers healing.
  \item \textbf{Dropped PQ-step messages}: If an authenticated $kem\_id$ entry or its matching
        ciphertext is
        permanently lost (rather than merely delayed), the PQ-initiator must timeout and
        re-initiate with a fresh keypair.  Retry policy is an implementation concern.
  \item \textbf{Skipped-key cache and PCS}: Keys cached in $\mathcal{K}_{skipped}$ before
        $t_{rec}$ remain compromised even after the PQ ratchet round-trip.
  \item \textbf{Confirmation tags and half-open sessions}: $tag_A$ gives Bob one-sided explicit
        key confirmation in $M_0$; the session is not mutually confirmed until Alice receives and
        verifies Bob's authenticated response $tag_B = \HMAC_{\mathrm{SHA3\text{-}256}}(K_{conf},
        \strlit{Bob} \| M_0^{core})$.  Until that response is received, Alice must treat the
        session as pending one-sided confirmation only and must not send application data that
        requires mutual confirmation guarantees.  A missing or unverifiable $tag_B$ is an
        authentication/availability failure, not implicit permission to proceed.
  \item \textbf{Deniability loss from transcript signatures:}
        Every PQ ratchet update carries a mutual ML-DSA-65 signature ($\sigma_{\mathrm{init}}$,
        $\sigma_{\mathrm{resp}}$) bound to both parties' long-term identity keys.  These signatures
        are publicly verifiable: any third party given the transcript and the identity public keys
        can cryptographically confirm that a conversation took place between $A$ and $B$.  This
        eliminates the deniability property present in the classical Double Ratchet, where ECDH
        key exchange provides implicit authentication but leaves no verifiable transcript evidence.
        The design choice is deliberate: mutual ML-DSA authentication is required for PCS against
        an adversary who has compromised symmetric ratchet state and could otherwise inject
        adversarial ciphertexts during recovery (Theorem~\ref{thm:single-update-pcs}).  Operators
        requiring deniability should consider alternative authentication mechanisms: ring-signature
        or group-signature schemes over identity keys (providing authentication without individual
        binding), MAC-based mutual authentication using a pre-established shared secret (as in the
        classical Double Ratchet), or a two-phase design where deniable implicit authentication
        covers normal messages and non-deniable explicit signatures are used only on signed ratchet
        updates, with the signed transcript treated as a recoverable attestation log rather than
        repudiable chat history.  Formal deniability in the post-quantum setting is an open
        problem explored in \cite{brendel2019deniability}.
\end{enumerate}

Signal's PQXDH \cite{signal_pqxdh} introduced post-quantum key encapsulation into the initial
handshake to provide PQ-FS against HNDL attacks.  Both PQXDH and Star-Mesh's PQ-X3DH achieve
asynchronous handshake completion by fetching pre-keys ahead of dialogue; what distinguishes
Star-Mesh is that pre-keys are distributed over a decentralized, serverless Kademlia DHT rather than
a trusted central server.  Under Apple's four-tier taxonomy of messaging security
(Levels~0--3) \cite{imessage_pq3}, initial-handshake-only PQC represents Level~2.  Reaching Level~3
requires post-quantum ratcheting throughout ongoing sessions.  Recently, Signal introduced the
Sparse Post-Quantum Ratchet (SPQR / Triple Ratchet) \cite{signal_spqr,dodis2025tripleratchet,auerbach2025compare}, developed jointly by Signal engineers and researchers from PQShield and academia.  SPQR integrates ML-KEM-768 into the Double Ratchet by streaming erasure-coded chunks of large KEM encapsulation keys ($1{,}184$~B) and ciphertexts ($1{,}088$~B) across successive conversational messages (sliced into small chunks, on the order of tens of bytes per message depending on erasure-coding parameters and transport framing) and overlapping ciphertext generation via the ``ML-KEM Braid'' to continuously derive fresh 32-byte post-quantum shared secrets.  Similarly,
Apple's iMessage PQ3 \cite{imessage_pq3} introduced periodic in-band ML-KEM re-keying (performing a post-quantum ratchet approximately every 50 messages) into a
centralized messaging service.

In contrast to the centralized transport assumed by SPQR and PQ3, Star-Mesh targets a decentralized
DHT and Sphinx mixnet setting.  Crucially, authentication in Star-Mesh is only partly post-quantum:
the initial handshake message $M_0$ is not digitally signed, and its initiator authentication rests
on classical $DH_1$; against a contemporaneous active CRQC during the initial handshake, $M_0$
authentication remains classical.  Star-Mesh's post-quantum authentication specifically covers
Bob's pre-key bundle (via an ML-DSA identity signature against DHT key substitution) and the
post-compromise ratchet recovery updates (via mutual ML-DSA \emph{UpdateAuth} signatures,
$\sigma_{\mathrm{init}}$ and $\sigma_{\mathrm{resp}}$), which are necessary to prevent an adversary
holding compromised symmetric ratchet state from injecting adversarial ciphertexts during recovery.

\paragraph{Session Protocol and Briar.}
Session \cite{session_protocol} routes messages through an onion network to achieve metadata
resistance and eliminates central servers.  Briar \cite{briar_design} routes through Tor.  Both
achieve excellent decentralization and metadata resistance but use exclusively classical X25519
for confidentiality, leaving them vulnerable to HNDL attacks.  Star-Mesh integrates hybrid PQC
into a similar decentralized architecture.
The technical obstacle these systems do not solve is the size incompatibility between
post-quantum primitives and onion-routing packet disciplines: Tor and Sphinx-based mixnets
enforce fixed-size cells or constant-size packets to prevent traffic analysis, but ML-DSA
signatures and ML-KEM ciphertexts exceed these bounds, requiring non-trivial fragmentation or
padding strategies that directly weaken the traffic-analysis resistance those networks are
designed to provide.

\paragraph{Double Ratchet Formal Analysis.}
Alwen, Coretti, and Dodis \cite{alwen2019doubleratchet} formalized the Double Ratchet by modularizing it into Continuous Key Agreement (CKA) and forward-secure AEAD, generalizing the ratchet to generic KEM-based constructions---the closest theoretical foundation for our asynchronous ML-KEM ratchet.
Cohn-Gordon et al.\ \cite{cohngordon2016} provided the first multi-stage formal security analysis of the
Signal Double Ratchet.  Cremers and Zhao \cite{cremers2024ratchet} extended this to a model capturing strong
compromise resilience, temporal privacy, and immediate decryption simultaneously.
Jaeger and Stepanovs \cite{jaeger2018optimal} derived optimal security bounds for ratcheted
key exchange, establishing tight separations between forward secrecy, post-compromise security,
and deniability that inform the trade-offs Star-Mesh makes.
Poettering and R\"osler \cite{poettering2018asynchronous} formalized asynchronous ratcheted key
exchange (ARKE) and showed that post-compromise recovery requires a minimum of one round-trip
under asynchronous delivery---consistent with our Corollary~\ref{cor:pcs}.
Bellare, Dowling, and Stebila \cite{bellare2017multi} analyzed multi-stage key exchange
security for the TLS handshake; their stage-based freshness predicates influenced the
oracle naming in Section~\ref{sec:secmodel}.
Our security model and argument structure are closely adapted from
\cite{cohngordon2016,cremers2024ratchet}, with aligned freshness/oracle semantics but
protocol-specific reformulation for the hybrid post-quantum setting with ML-KEM.

Post-quantum ratchet recovery after a bounded number of epochs has been studied by
Auerbach et al.\ \cite{auerbach2025compare} in the context of SPQR; Star-Mesh's explicit
contribution is the combination of (i) a formal pre-recovery exposure window under
RNG-recovery, deletion, and asynchronous delivery assumptions, (ii) decentralized
pre-key distribution over a Kademlia DHT without a trusted server, and (iii) the
mixnet-level burst fingerprint analysis and mitigations in Section~\ref{sec:metadata}.
The technical obstacle these analyses leave open is the adaptation of ratchet freshness
semantics to KEM-based key exchange: classical DH-ratchet models assume commutativity and
ephemerality properties that do not hold for KEMs, where the encapsulator and decapsulator
roles are asymmetric and static public keys must be pre-distributed, forcing a new formal
treatment of RNG-compromise recovery and one-time pre-key exhaustion that is absent from
existing Double Ratchet proofs.

\paragraph{PQ-MLS and Group Messaging.}
RFC~9420 \cite{rfc9420} defines the base Messaging Layer Security (MLS) protocol for
centralized group messaging; post-quantum extensions to MLS are an active area of
standardization effort.  Star-Mesh targets asynchronous pairwise messaging over a DHT.
The two protocol classes are complementary and address different deployment scenarios.
The technical obstacle that prevents MLS-style designs from operating over a decentralized
DHT is their dependence on a central Delivery Service to impose a total ordering on group
operations and maintain tree consistency: without such a server, concurrent pre-key updates
produce conflicting tree states that cannot be resolved without a global coordination
mechanism, a problem that does not arise in Star-Mesh's pairwise ratchet setting.  A plausible
future direction is D-MLS: use a CRDT operation set for signed proposals and commits, retain the
MLS parent tree hash and confirmation-tag checks, and apply a deterministic winner rule to
concurrent valid commits.  This would provide convergence for clients with the same operation
set, but would not itself provide Byzantine consensus or prevent DHT eclipse and fork attacks;
the full design and required security tests are left to a separate research track in
\texttt{docs/d-mls-design.md}.

\paragraph{Hybrid KEM Composition.}
Giacon et al.\ \cite{giacon2018kem} proved that the concatenation combiner for KEMs
achieves IND-CCA2 security if either component KEM is IND-CCA2 secure, provided the KEM ciphertexts are bound into the KDF input and the combiner
uses a suitable KDF modeled as a PRF (as established in \cite{giacon2018kem}).  Our
hybrid KEM construction satisfies this precondition by binding the ciphertexts $ct_1, ct_2$ and the ephemeral public key $EK_{pk,A}$ into the HKDF $info$ parameter, applying the composition results of \cite{giacon2018kem} with HKDF as
the PRF (Assumption~\ref{asm:hkdf}).
However, these static composition results do not extend to the stateful ratcheting setting:
they bound the advantage of a single IND-CCA2 distinguisher against a one-shot encapsulation,
but do not address the session-level forward secrecy and post-compromise recovery properties
that arise when KEM shared secrets are fed into a continuously updated ratchet state machine
where cached skip-keys and out-of-order delivery create additional exposure windows.

\paragraph{Metadata Resistance.}
Chaum \cite{chaum_mix} introduced mix networks; Piotrowska et al.\ \cite{loopix} developed the
Loopix architecture providing provable anonymity under formal assumptions.  The Sphinx packet
format \cite{sphinx} provides onion encryption with constant-size packets.  Star-Mesh inherits these results
directly for its routing layer.
The technical obstacle these systems leave unaddressed is the integration of large
post-quantum key material into a constant-packet-size discipline: Loopix's anonymity proof
assumes all packets are padded to a fixed size, but ML-DSA-87 signatures ($>4.5$~KB) and
ML-KEM-1024 ciphertexts ($1.5$~KB) far exceed standard Sphinx MTUs, and na\"ively introducing
these payloads forces perpetual fragmentation or re-padding that invalidates the constant-size assumption
on which the anonymity bound depends.  Star-Mesh bounds this by selecting Category~3
parameters (ML-KEM-768, ML-DSA-65), which allow intermediate conversational messages to fit within
standard 1{,}500-byte MTU bounds without fragmentation, confining multi-packet Sphinx trains to periodic
authenticated KEM updates (4 fragments every $\Delta$ messages) and the initial session handshake ($M_0$),
as detailed in Section~\ref{sec:paramselection}.

% ============================================================
\section{Conclusion}
\label{sec:conclusion}
% ============================================================

We introduced a windowed view of recovery in an asynchronous hybrid KEM ratchet.  The central
artifact is a state machine for authenticated ML-KEM exchanges under delay, loss, duplication,
replay, and out-of-order delivery, together with a freshness game that makes RNG recovery and
secret deletion explicit.  This view turns recovery into a measurable transition: after
compromise, a cleanly generated ML-KEM keypair and a completed authenticated round-trip yield
fresh post-recovery message keys, while the messages sent before completion occupy an exposure window
governed by $\Delta$ messages of counter delay plus network round-trip latency (unbounded if the peer is offline).
The parameter $\Delta$ exposes the design trade-off directly:
smaller intervals shorten pre-recovery exposure, while larger intervals amortise KEM traffic.

The resulting theorem has explicit delivery and implementation assumptions and targets the
recovery transition itself.  ML-DSA authenticates the signed bundle and every periodic ratchet update;
X25519 remains a classical hybrid component, while ML-KEM supplies the recovery contribution
against a quantum-capable adversary.  The Rust prototype exercises the concurrent implementation
state machine and the ProVerif models check selected symbolic invariants.  The cryptographic
wire-cost of the post-quantum ratchet is $88.90$ amortised bytes per message at $\Delta=50$,
which fully accounts for the mutual ML-DSA-65 identity signatures on every update required to
guarantee post-compromise security under state compromise (excluding DHT overlay maintenance
and mixnet cover traffic).

Key assumptions underlying the pairwise recovery bound are: Module-LWE hardness
(Assumption~\ref{asm:mlwe}), ML-DSA unforgeability (Assumption~\ref{asm:mldsa}), the deletion
schedule being enforced by the implementation (Assumption~\ref{asm:deletion}), a clean RNG from
$t_{rec}$ onward (Assumption~\ref{asm:rng}), and the dual-PRF / one-uniform-component extractor
KDF security (Assumption~\ref{asm:kdf-hi}).  The DHT availability and mixnet assumptions are relevant only
to deployment-context discussions and do not enter the pairwise confidentiality theorem.

\paragraph{Research Positioning.}
The contribution is a protocol-design and security-analysis framework for reasoning about
asynchronous recovery as a timed, stateful transition.  It provides a basis for implementation
and deployment work; production use would additionally require implementation hardening,
empirical evaluation, interoperability testing, formal verification, and operational
abuse-resistance analysis.

\paragraph{Future Work.}
Several directions remain open.  First, a full composable security proof (e.g., in the UC
framework \cite{uc_framework}) for the complete protocol would be desirable; the present
ProVerif models provide symbolic evidence but not a computational composable treatment.
Second, group messaging extensions analogous to PQ-MLS \cite{rfc9420} should be explored
for the DHT setting.  Third, an implementation and empirical performance evaluation on
resource-constrained devices (IoT, mobile) would validate the practical viability of the
design.  Fourth, the confirmation-tag mechanism for $M_0$ requires a full mutual-confirmation
response path and computational analysis under replay, timeout, and transcript-rebinding attacks.

\appendix
\section{Complete Protocol State Machine and Message Framing}
\label{sec:appendix-statemachine}
% ============================================================

This appendix provides the full, normative specification of the Star-Mesh state machine,
message framing, asynchronous concurrent KEM buffer, and staged commit rules.

\subsection{Endpoint State Representation}
Each communicating peer maintains a persistent state record containing the following fields:
\begin{itemize}
  \item \textbf{Session context:} Session ID $\mathsf{sid} \in \bits^{32}$ and protocol role $\mathsf{role} \in \{\mathrm{init}, \mathrm{resp}\}$.
  \item \textbf{Identity keys:} ML-DSA-65 keypair $(IK^{DSA}_{sk}, IK^{DSA}_{pk})$ (hardware-isolated) and classical keypair $(IK^{DH}_{sk}, IK^{DH}_{pk})$.
  \item \textbf{Symmetric roots:} Current root key $RK \in \bits^{32}$, live entropy pool $EP \in \bits^{32}$.
  \item \textbf{Directional chain keys:} Active sending chain key $CK_s \in \bits^{32}$ and counter $N_s \in \mathbb{N}$; active receiving chain key $CK_r \in \bits^{32}$ and counter $N_r \in \mathbb{N}$; previous chain length $PN_s \in \mathbb{N}$.
  \item \textbf{Classical DH ratchet state:} Local ephemeral keypair $(DH^{loc}_{sk}, DH^{loc}_{pk})$ and remote public key $DH^{rem}_{pk}$.
  \item \textbf{Asynchronous KEM buffer state:}
    \begin{itemize}
      \item $\mathsf{pq\_send\_seq}, \mathsf{pq\_recv\_seq} \in \mathbb{N}$ (monotonic update counters).
      \item $PQ^{\mathrm{outstanding}}$: Map $\mathsf{kem\_id} \mapsto (PQ^{loc}_{sk}, \mathsf{epoch}, \mathsf{timestamp})$ tracking local KEM proposals awaiting peer response.
      \item $PQ^{\mathrm{incoming}}$: Map $\mathsf{kem\_id} \mapsto (SS_{PQ}, ct, \mathsf{seq})$ buffering completed responses for in-order application.
      \item $PQ^{\mathrm{retired}}$: Bounded FIFO set of retired $\mathsf{kem\_id}$ values (capacity 256) preventing replay.
      \item $\mathsf{pq\_step\_counter} \in \{0, \dots, \Delta\}$ (ratchet interval countdown).
      \item $\mathsf{transcript\_hash} \in \bits^{32}$ (running hash of accepted ratchet updates).
    \end{itemize}
  \item \textbf{Out-of-order skipped keys:} $\mathcal{K}_{skipped}$, a bounded cache (capacity $N_{\mathrm{cache}} = 1{,}000$) mapping $(DH^{rem}_{pk}, N) \mapsto MK_N$.
\end{itemize}

\subsection{Canonical Message Framing and Associated Data}
Every transmitted packet $m_{\mathrm{wire}} = (h, c)$ carries an unencrypted plaintext header $h$:
\[
  h = \bigl(\mathsf{sid},\; DH^{loc}_{pk},\; N_s,\; PN_s,\; \mathsf{flags},\; \mathsf{ext}\bigr).
\]
The flag byte $\mathsf{flags}$ encodes the presence of asymmetric ratchet extensions:
\begin{itemize}
  \item $\mathsf{FLAG\_KEM\_INIT} = \hexlit{0x01}$: $\mathsf{ext}$ contains $(kem\_id, PQ^{loc}_{pk}, \sigma_{\mathrm{init}})$.
  \item $\mathsf{FLAG\_KEM\_RESP} = \hexlit{0x02}$: $\mathsf{ext}$ contains $(kem\_id, ct, \sigma_{\mathrm{resp}})$.
  \item $\mathsf{FLAG\_REGULAR} = \hexlit{0x00}$: routine conversational message ($\mathsf{ext} = \varepsilon$).
\end{itemize}
The Associated Data $AD_m$ for AES-256-GCM authenticated encryption is defined as:
\[
  AD_m \coloneqq \strlit{StarMesh-Header-v1} \,\|\, \flen{h} \,\|\, h.
\]
The ciphertext is computed as $c \getsr \mathsf{AES\text{-}256\text{-}GCM}\text{-}\mathsf{Enc}(MK_i, N_s^{32} \,\|\, \mathbf{0}^{64}, AD_m, m)$.

\subsection{Canonical Asymmetric Update Signatures}
The mutual authentication signatures $\sigma_{\mathrm{init}}$ and $\sigma_{\mathrm{resp}}$ are computed over canonical transcripts:
\begin{align*}
  m_{\mathrm{init}} &\coloneqq \strlit{UpdateAuth-Init} \,\|\, \mathsf{sid} \,\|\, \mathsf{kem\_id} \,\|\, PQ^{loc}_{pk} \,\|\, \mathsf{epoch} \,\|\, \mathsf{prev}, \\
  \sigma_{\mathrm{init}} &\getsr \MLDSA.\Sign\bigl(IK^{DSA}_{sk,\mathrm{init}},\, m_{\mathrm{init}}\bigr), \\
  m_{\mathrm{resp}} &\coloneqq \strlit{UpdateAuth-Resp} \,\|\, \mathsf{sid} \,\|\, \mathsf{kem\_id} \,\|\, PQ^{loc}_{pk} \,\|\, ct \,\|\, \mathsf{epoch}' \,\|\, \mathsf{prev}', \\
  \sigma_{\mathrm{resp}} &\getsr \MLDSA.\Sign\bigl(IK^{DSA}_{sk,\mathrm{resp}},\, m_{\mathrm{resp}}\bigr),
\end{align*}
where $\mathsf{prev}$ and $\mathsf{prev}'$ are the running transcript hashes of the respective last accepted updates.

\subsection{Asynchronous KEM Buffer State Transitions}
Because ML-KEM shared secrets are not commutative, updates must be applied in a deterministic, synchronized order:
\begin{enumerate}
  \item \textbf{Proposal Generation:} When $\mathsf{pq\_step\_counter} = 0$, the initiator generates $(PQ^{loc}_{sk}, PQ^{loc}_{pk}) \getsr \MLKEM.\KeyGen(1^\lambda)$, derives
    \[
      \mathsf{kem\_id} \gets \mathsf{BLAKE3}\bigl(\strlit{StarMesh-KEM-v1} \,\|\, \mathsf{sid} \,\|\, PQ^{loc}_{pk} \,\|\, \mathsf{pq\_send\_seq}\bigr),
    \]
    records it in $PQ^{\mathrm{outstanding}}$, and transmits with signature $\sigma_{\mathrm{init}}$.
  \item \textbf{Responder Advance:} The responder verifies $\sigma_{\mathrm{init}}$ and ensures $\mathsf{kem\_id} \notin PQ^{\mathrm{retired}}$. It computes $(ct, SS_{PQ}) \getsr \MLKEM.\Encaps(PQ^{loc}_{pk})$, generates $\sigma_{\mathrm{resp}}$, and executes the 96-byte derivation:
    \begin{align*}
      EP' &\gets \HKDF(SS_{PQ},\; EP,\; \strlit{StarMesh-EntropyPool} \,\|\, ct,\; 32), \\
      (RK',\, \vec{CK}) &\gets \HKDF(SS_{PQ},\; EP',\; \strlit{StarMesh-PQ-RK},\; 96),
    \end{align*}
    where $\vec{CK} = (CK_{A\to B}, CK_{B\to A})$.  It sets $RK \leftarrow RK'$, $CK_r \leftarrow CK_{A\to B}$, $CK_s \leftarrow CK_{B\to A}$, $EP \leftarrow EP'$, zeroizes $SS_{PQ}$, resets $\mathsf{pq\_step\_counter} \leftarrow \Delta$, and returns $(kem\_id, ct, \sigma_{\mathrm{resp}})$.
  \item \textbf{Initiator In-Order Draining:} The initiator verifies $\sigma_{\mathrm{resp}}$, decapsulates $SS_{PQ} \gets \MLKEM.\Decaps(PQ^{loc}_{sk}, ct)$, executes the identical derivation, sets $RK \leftarrow RK'$, $CK_s \leftarrow CK_{A\to B}$, $CK_r \leftarrow CK_{B\to A}$, $EP \leftarrow EP'$, zeroizes $PQ^{loc}_{sk}$ and $SS_{PQ}$, retires $\mathsf{kem\_id}$, and resets $\mathsf{pq\_step\_counter} \leftarrow \Delta$.
  \item \textbf{Replay and Timeout Handling:} Any received $\mathsf{kem\_id} \in PQ^{\mathrm{retired}}$ is immediately discarded without updating state. If an outstanding proposal times out without reply, the record is retired without changing $RK$, and a fresh proposal with a new sequence number is initiated on retry.
\end{enumerate}

\subsection{Max-Skip Bound and Staged Commit-After-Authentication}
To prevent denial-of-service and chain key destruction from unauthenticated packets:
\begin{enumerate}
  \item \textbf{Max-Skip Threshold:} If $N - N_r > N_{\mathrm{max\_skip}} = 1{,}000$, the packet is immediately dropped.
  \item \textbf{Staged Key Derivation:} The receiver creates a temporary scratch state $CK_{\mathrm{temp}} \leftarrow CK_r$. It derives candidate skipped keys $MK_j$ for $j \in \{N_r, \dots, N-1\}$ and the target key $MK_N$ without modifying live state.
  \item \textbf{Verification and Conditional Commit:} The receiver evaluates
    \[
      m \gets \mathsf{AES\text{-}256\text{-}GCM}\text{-}\mathsf{Dec}\bigl(MK_N,\; N^{32} \,\|\, \mathbf{0}^{64},\; AD_m,\; c\bigr).
    \]
    \begin{itemize}
      \item If authentication succeeds: $\{MK_{N_r}, \dots, MK_{N-1}\}$ are committed to $\mathcal{K}_{skipped}$, $N_r \leftarrow N + 1$, and $CK_r \leftarrow CK_{\mathrm{target}}$. $MK_N$ is zeroized after decryption.
      \item If authentication fails: the scratch buffer is immediately zeroized and discarded. Live $CK_r$, $N_r$, and $\mathcal{K}_{skipped}$ remain strictly unmodified.
    \end{itemize}
\end{enumerate}
